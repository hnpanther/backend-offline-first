## What this project is

Spring Boot **4.1** / Java **25** backend for an industrial **offline-first round / log-sheet** system:

- **Web admin** (Thymeleaf + session form-login) — master data, templates, RBAC, reports, batch Excel import.
- **Mobile API** (`/api/**`, JWT) — inbox, claim/release, batch complete, NFC lookup, per-sheet **bundle**.
- **PostgreSQL** schema owned by Flyway — `V1__initial_schema.sql` is a **closed baseline**; every change since is a new `V{n}` (see §2). [docs/schema.md](docs/schema.md) describes the current schema table by table.
- Server is **authoritative** for log-sheet lifecycle; clients use idempotency keys (`local_id`, `client_action_id`).

Default URL: `http://localhost:8081`. Default bootstrap admin: `admin` / `admin123` (change immediately).

## Architecture (layered modular monolith)

```
HTTP
 ├── controller/   REST /api/**  (JWT, CSRF off)     ──┐
 └── web/          Thymeleaf panel (session login)  ──┼──► service/ ──► repository/ ──► PostgreSQL
                                                      │
config/WebSecurityConfig  (dual filter chains) ───────┘

aspect/     LoggingAspect + RepositoryAuditAspect (audit → async AuditWriteService)
scheduler/  LogSheetScheduler → generation + expiry
```

**Not** hexagonal / clean-architecture ports. Keep layers:

| Layer | Role |
|---|---|
| `controller/`, `web/` | Thin: auth annotations, bind params, call services, map UX |
| `service/` | Business rules, uniqueness, hierarchy, lifecycle, unit scope |
| `repository/` | Spring Data JPA (+ ancestry projections, native scope SQL) |
| `entity/` | JPA model; timestamps = **epoch millis `Long`** |
| `domain/` | Enums / validation helpers (not entities) |
| `dto/` | API and transfer objects |
| `ui/` | Persian mapping, flash helpers (`ErrorTranslator`, `FaMessages`, …) |
| `security/` | JWT (+ `jti` session registry check), LDAP bind, `PermissionCodes`, user details |
| `config/` | Security, async pools, LDAP, admin/import recovery runners |
| `aspect/`, `audit/`, `logging/` | Cross-cutting logging + field-level audit |
| `util/`, `mapper/` | Excel, Jalali, NFC, labels, small mappers |
| `service/importjob/` | Async batch Excel jobs |

**Request pattern:** `@PreAuthorize` on controller → service (extra unit/supervisor rules) → repository. Do **not** put business or scope rules only in controllers or templates.

## Domain map (short)

- **Hierarchy:** Location → PlantSystem → MainFunction → SubFunction → **AssetEntry**  
  Owned by `AssetHierarchyService` (direct parent + denormalized ancestry + cascade + template scope walks).
- **Asset ↔ SubFunction:** one **ACTIVE** asset per sub-function, unlimited **inactive** ones (`ux_asset_entries_active_sub_function`, a *partial* unique index, + `MasterDataUniquenessValidator`). Inactive assets remain NFC-findable but are **excluded from log-sheet preview/generation**. See gotcha #29 for the equipment-replacement contract.
- **Log sheets:** Generated from templates (manual/scheduled) **or created as custom/template-less sheets** via `CustomLogSheetService` + web `POST:/log-sheets/custom` (asset search `GET:/log-sheets/options/assets`). Supervisor picks **active** assets in a supervised unit; assets may span multiple classes; `template_id = null`; name → `template_name`; multi-class `field_definitions_snapshot` via `LogSheetFieldDefinitionsService.captureSnapshot(Collection)`. UI requires due date; service validates future `dueAt` when set. Created `PENDING` / `MANUAL`, then same claim/assign/complete/expire lifecycle. **`VOIDED`** soft-invalidates a `SUBMITTED` sheet (admin or unit supervisor: `POST:/log-sheets/{id}/void` / `unvoid`); excluded from parameter reports; restorable only to `SUBMITTED`. Reopen submitted → draft with new due: `POST:/log-sheets/{id}/reopen` (admin or unit supervisor). Optional web-only `notes` on the sheet (fill/complete). Late offline completes → `log_sheet_void_submissions`.
- **Mobile sessions:** `/api/**` JWTs are stateful — every token carries a `jti` backed by an `api_sessions` row (`ApiSessionService`). `JwtAuthenticationFilter` rejects a token whose row is missing, revoked, or expired, so signature validity alone is **not** enough. Login registers device/UA/IP and **supersedes** the user's other live sessions (one device per user). Admin page `/api-sessions` lists and revokes; token lifetime stays in `app_settings['auth.jwt.expiry_minutes']`. Revocation only bites when the device is online — that is by design for offline-first.
- **Web sessions:** the panel enforces **one concurrent session per user** via Spring's concurrent session control (`maximumSessions(1)` + in-memory `SessionRegistryImpl` + `HttpSessionEventPublisher` in `WebSecurityConfig`); a new login expires the old browser → `/login?expired`. Idle timeout: `server.servlet.session.timeout=60m`. `AppUserDetails.equals/hashCode` identify a principal **by user id** (see gotcha #82) — required for the limit, and by id rather than by username because a rename used to change a session's identity and defeat it. `WebSessionMetadataStore` (in-memory) keeps IP/UA/login time; admin page `/web-sessions` (`WebSessionService`) lists/expires sessions addressed by a SHA-256 digest key — never expose raw `JSESSIONID`s. No DB table on purpose: sessions are non-persistent across restarts.
- **Integration API:** `/integration/v1/**` — read-only, third-party, authenticated by an `X-API-Key` header on its **own** `SecurityFilterChain` at `@Order(0)`. No user, no session, no JWT, no role, and deliberately **no permission row** (there is no principal for a role to describe — the chain is the gate). Returns **finished** log sheets only (`SUBMITTED`/`VOIDED`/`EXPIRED`/`CANCELLED`), and that filter is a literal inside `LogSheetRepository.findExposableToIntegration`, not just caller-side validation. Keys live in `api_keys` (`lsk_<keyId>_<secret>`, SHA-256 of the secret stored, shown once, revoke-never-delete); every request including refusals is recorded in `api_key_usage`. Admin page `/integration-keys` (ADMIN). Dedicated DTOs under `dto/integration` — never reuse the mobile DTOs or entities here, or the next internal column added leaks. See gotcha #77 before adding another filter.
- **RBAC:** Permission code = `METHOD:path` (one DB row per **authority**; export/options/draft/bulk paths often reuse a parent authority). System roles: `ADMIN`, `HIGH_USER`, `SUPERVISOR`, `SENIOR_OPERATOR`, `OPERATOR`. Unit scope via `unit_supervisors` / `unit_operators` + `OperationalUnitScopeService`. Endpoint permission ≠ full access — check service rules (e.g. supervisor create-only templates; custom sheet unit + asset scope). Custom-create permissions are Flyway-seeded for `ADMIN` / `HIGH_USER` / `SUPERVISOR`.
- **Mobile data:** Lightweight `GET /api/bootstrap` = unit context only. Plant/assets for a round come from **`GET /api/log-sheets/{id}/bundle`**. Bundle already supports multi-class entries/fields and null `templateId` — custom sheets need no PWA change. Do not restore a full master-data delta bootstrap unless explicitly requested.
- **Batch import:** `/batch-import` → disk under `app.import.storage-path` (default `./data/imports`) + `import_jobs`. One active job system-wide; max **10 000** rows; sequential async pool.
- **Mobile sync batch cap:** `POST /api/log-sheets/batch` runs synchronously in one DB transaction per request (not async/queued like batch import) — it rejects over `app.sync.batch-max-items` (default **500**) with a `400` before touching the DB. Checked in `LogSheetService.submitBatch`, first line. If you add another sync-batch endpoint, apply the same guard rather than assuming client-side chunking.

## Conventions agents MUST follow

### 1. Business logic location
- New rules → `service/`.
- Controllers stay thin.
- Hierarchy mutations → `AssetHierarchyService` (do not reimplement cascade in controllers).

### 2. Flyway / schema
> ⚠️ **V1 is a closed baseline. Every schema change is a NEW `V{n}__description.sql`.**
> This reverses the earlier fold-into-V1 practice, on the user's instruction (2026-08-14):
> *"هر تغییری تو schema نیاز بود رو از این به بعد داخل v2 بریز"*. Do not edit an applied
> migration — its Flyway checksum will disagree with the database and the app refuses to boot.
> The old fold recipe (delete history rows, hand-patch the checksum, reboot twice) is **no
> longer used and should not be reintroduced.**

- **📖 [docs/schema.md](docs/schema.md) is the reference for what the schema looks like now** —
  every table, column, index and constraint with the reasoning, in one place rather than
  scattered across migration files. Reading `V1 → V2 → V3` and replaying them mentally is the
  slow, error-prone way to answer "what does this table look like?".
- Migration files: `src/main/resources/db/migration/`
  - `V1__initial_schema.sql` — the baseline (everything up to 2026-08-05 was folded in here
    while the app was greenfield). **Closed.**
  - `V2__reading_time_and_import_heartbeat.sql` — `asset_status_change_requests.reading_recorded_at`, plus `import_jobs.heartbeat_at` (two changes consolidated while development-only; do not merge into it again)
  - `V3__capabilities_integration_api_and_answered_form_data.sql` — **everything between the V2
    release and the next one, in one file.** The eleven `CAP:*` rows and their grants;
    `users.org_unit` / `users.org_position`; the three mobile policy settings; the whole
    Integration API (`api_keys`, `api_key_usage`, four `/integration-keys` admin permissions
    granted to `ADMIN` only, `idx_log_sheets_status_finalized_at`); `audit_log.actor_user_id`
    losing its foreign key altogether (gotcha #84); and the `form_data` repair
    that drops keys nobody answered (gotchas #87–#88). It was developed as four separate
    migrations and consolidated because **no operational database has ever run any of them —
    production is still on V2** — so production advances by one version rather than four for
    changes it has never seen. See gotcha #86 for the repair that collapsing them required on
    development databases.
- `spring.jpa.hibernate.ddl-auto=validate` — schema comes from Flyway only. A successful boot is
  therefore also proof that every entity column exists in the schema.
- **A new migration applies automatically on the next boot.** No checksum realignment, no manual
  `flyway_schema_history` edits. That is the entire point of leaving V1 alone.
- **Every migration after V1 must explicitly grant its own new permissions** to `ADMIN` (and
  `HIGH_USER` where relevant). V1's blanket `CROSS JOIN` grant was a one-time snapshot taken when
  V1 ran; it does not retroactively cover rows a later migration inserts. See gotcha #22 — this
  failure is invisible to the test suite and was only caught by a live admin login.
- After adding a migration, **update [docs/schema.md](docs/schema.md) in the same commit.**

### 2b. New endpoints → permissions (mandatory)

**One `permissions` row per authority** (`code = METHOD:path`). Authorities are **manual**, not auto-generated from `@RequestMapping`.

Several handlers intentionally **reuse** an existing authority (no extra DB row): e.g. `GET …/export` and `GET …/options/…` → parent list `GET:/…`; `POST …/delete-bulk` → `POST:/…/{id}/delete`; `POST /log-sheets/{id}/draft` → `POST:/log-sheets/{id}/complete`; batch-import cancel/errors → `GET` or `POST:/batch-import`. The number of `@PreAuthorize` mappings can exceed the number of seeded permissions.

Whenever you add a handler that checks a **new** authority string:

1. Add `PermissionCodes` constant.
2. Add `@PreAuthorize("hasAuthority('METHOD:/path')")` on the handler(s).
3. **Create/update the permission through a Flyway migration** — `INSERT` into `permissions`, plus `role_permissions` for any system role that should get it (beyond what V1 already grants to `ADMIN`).

| Environment | How to ship the permission |
|---|---|
| Any DB that already ran the earlier scripts | Add a **new** Flyway script (`V3__add_….sql`, …). **Required** for shared/staging/production. |
| Any schema or seed change | Add a new `V{n}__description.sql` — including its own explicit `role_permissions` grants (gotcha #22). V1 is closed. |

**Forbidden:** creating the permission only in the Roles UI, only with ad-hoc SQL, or only in Java bootstrap — other environments will miss it and `@PreAuthorize` will deny everyone.

### 3. Uniqueness
- Use `MasterDataUniquenessValidator` for web + Excel (codes, tags, names, NFC, field keys, one-asset-per-SF).
- Import: `*ForImport` + `FileUniqueness` (in-file + DB).
- When updating managed entities that participate in unique indexes: **validate on a detached candidate first**, then copy onto the managed entity (see `AssetEntryService.update`) — avoids Hibernate auto-flush mid-check. Same precaution applies to any throwing validation on a managed entity under Open Session In View, not just uniqueness — e.g. `AssetClassWebController.updateField` computes/validates `FieldValidationSupport.build(...)` (throws on warning/danger `min > max`) **before** mutating the fetched `FieldDefinition`, so a rejected edit leaves the existing row completely untouched rather than partially dirtied.

### 4. i18n / errors
| Layer | Language |
|---|---|
| Services, validators, import row messages | **English** |
| Web flash / API JSON | **Persian** via `ErrorTranslator`, `FaMessages`, `ImportDisplay`, `ApiResponseSupport` |

Always add translator mappings for new English messages (or users see raw English / generics). Map new unique constraint names in `ErrorTranslator.dataIntegrityViolation` when adding indexes.

### 4b. Authorization: never branch on a role's code
- **No `isAdmin()`, no `hasRole()`.** They do not exist any more. A rule written against a role's *code* is not inherited by a role duplicated from it — the copy gets a new code — which made "ساخت نقش مشابه" quietly produce a role that held every permission and still got access denied.
- Decisions that are not about an endpoint are **capabilities**: `CAP:*` rows in `permissions` (`category='capability'`, null method/path), read with `SecurityUtils.hasCapability(...)`. They live in that table so role duplication copies them for free.
- **Phrase them positively** — absence must mean restricted. `isUnitScopedOnly()` is the one place the negation is written.
- Adding one: constant in `Capabilities` (+ `ALL`), row and grants in a new `V{n}`, entry in `SystemRoleCapabilities`, then use it. `CapabilitySeedIntegrationTest` fails if the migration and the map drift; `NoRoleCodeAuthorizationTest` fails the build if a role-code check reappears.
- Unit **scope** (`isSupervisorOf`, `getAccessibleUnitIds`) is a different axis and stays as it is — capabilities say what kind of actor you are, scope says which units you own.
- **The five system roles are immutable and undeletable** (`RoleService.assertNotSystemRole`). Customising goes through duplication — which works properly now that access is permission-based. Do not add an "edit system role" escape hatch; it would desynchronise the seed, `SystemRoleCapabilities` and the docs at once.
- **The last active administrator cannot be deleted, deactivated, or have ADMIN removed** (`UserService.assertNotOrphaningAdministration`). All three orphan the system. The rule keys off "last *active* admin", never a username.
- 📖 [docs/security.md](docs/security.md) §3 has the eleven capabilities, the grant matrix and the rules.

### 5. Security
- Every **new authority** in `@PreAuthorize`: matching Flyway-seeded `permissions` row (see §2b). Reuse an existing authority when the URL is a variant of an existing capability (export/options/draft). Skipping the migration leaves the endpoint unreachable or inconsistently granted across environments.
- Dual chains in `WebSecurityConfig`: `/api/**` JWT; web session.
- Auth types: `LOCAL` | `ACTIVE_DIRECTORY` | `HYBRID` — AD verifies password only; roles stay in DB.
- Never commit secrets (JWT, LDAP, DB passwords). Use env / gitignored `application-local.properties`.
- `LoginAttemptService` (in-memory, per-username) throttles both `/api/auth/login` and web `/login` — checked in `AppAuthenticationProvider.additionalAuthenticationChecks` **before** `verifyPassword()`, so a locked username never reaches the LDAP bind. This exists specifically to stop an attacker from using this app's login to trip Active Directory's own account-lockout policy against a real employee (no password guess needed — just their username). Don't move the lock check after password verification.
- Admin page `/login-attempts` (`LoginAttemptWebController.java`, `ADMIN` only) lists currently-locked usernames and ones approaching the threshold, with a manual "unlock" button (`LoginAttemptService.unlock`). Lock state is always recomputed from the clock at read time (never cached), so unlocking is a plain, always-safe map removal — including when clicked after the lock already expired naturally.

- Unit: `*Test.java` next to concern (Mockito, no DB).
- Integration: `*IntegrationTest` extends `support/AbstractPostgresIntegrationTest` (Testcontainers PostgreSQL + Flyway). **Docker required**.
- Security helpers: `@WithAppUser` in `support/`.

### 7. UI patterns (admin)
- List pages: text search `q` + pagination (`WebListSupport`) — **do not** add cascading multi-select filters on lists unless asked.
- Form parent pickers: AJAX typeahead (`MasterDataOptionsService` / options endpoints).
- Prefer existing Bootstrap + Thymeleaf patterns over new design systems.

### 7b. Master-data forms with large tables
- ~600 operational units and thousands of assets: form pickers must be **searchable remote** components (`remote-select.js` for one value, `remote-multi-select.js` for many), never a full table dump into a `<select>`. See gotcha #32.

### 8. Scheduling / templates
- Preserve `log_sheet_templates.next_run_at` on non-schedule edits.
- A template's assets come from **either** its scope+class (`SCOPE`) **or** a frozen `log_sheet_template_assets` list (`EXPLICIT`) — see gotcha #28 before touching generation, and never re-resolve an EXPLICIT template from its scope.
- Property `app.scheduler.log-sheet-max-backfill` defaults to **`0`** in `application.properties` (skip multi-occurrence backlog; single due tick still generates). Do not “fix” docs by changing behaviour silently.

### 9. Audit / logging
- Do not disable repository audit for production convenience.
- Cover both `save` and `saveAndFlush` if touching audit aspects.
- SVC/REPO logs are **DEBUG** by design (Import would explode at INFO).
- **Four log files, one question each**: `app.log` (narrative), `business.log` (what the system did), `audit.log` (who changed a row), `error.log` (failures). Adding a high-volume stream to `business.log` is how it became unreadable once already — give it its own logger and appender instead. Audit goes through `AuditTrailLogger`, never `BusinessEventLogger`.
- Text is the default layout; `SPRING_PROFILES_ACTIVE=json-logs` switches all four files to JSON for Filebeat/Logstash. If you add an appender, give it **both** branches or it silently keeps the text encoder in JSON mode.
- New MDC keys automatically become JSON fields. Keep them named for a reader (`errorId`, not `eid`), and add internal bookkeeping keys to `<excludeMdcKeyName>`.
- `auditExecutor` uses **`CallerRunsPolicy`** — that is load-bearing, not tuning. It is the only thing standing between a bulk write loop and `TaskRejectedException` thrown into that loop. Do not swap it back to the default abort policy; see gotcha #68.
- A type in `AuditEntitySupport.EXCLUDED_TYPES` is excluded because auditing it would be *harmful*, not merely noisy — `ImportJob`/`ImportJobError` are there so that writing a job's status never depends on the audit queue that job is saturating. Excluding an entity users actually care about is a different decision; do not add one casually.

### 9b. State-changing `fetch()` from the panel
- Always go through **`AppCsrf.postJson()`** (`static/js/csrf.js`). A bare `fetch(url, {method:'POST'})` is silently swallowed — see gotcha #69, which cost two dead buttons.
- Surface failures. `res.ok` alone is not enough when the access-denied handler redirects; check the answer is really JSON and show the user something.

### 9d. A null parameter inside `LOWER(CONCAT(…))` has no type
- **`:q IS NULL OR LOWER(a.code) LIKE LOWER(CONCAT('%', :q, '%'))` fails when `:q` really is null** — `function lower(bytea) does not exist`. PostgreSQL resolves functions while *planning*, so the `IS NULL` branch never gets a chance to short-circuit, and an untyped null binds as `bytea`. Use `COALESCE(:q, '')`: the empty-string literal gives the parameter a text type, and `LIKE '%%'` is what "no search term" already means.
- **It only breaks when every optional filter is absent**, which is the page's default load — the one request nobody writes a test for. The asset list shipped with tests for search-only and class-only and neither caught it; a smoke test that simply asked every panel page for a 200 did. Worth keeping that habit: one broad "does this page still render" test is worth several precise ones.

### 9b-2. The logging aspect serialises arguments and results — so what reaches it matters
- **`LoggingAspect` wraps every class under `controller..*`, `web..*` (minus `advice` and `support`), `service..*` and the repositories, and writes the arguments and the return value as JSON.** That is fine for the values this application passes around and catastrophic for framework objects. A new MVC interceptor placed in `web.support` received the **handler** as an argument; for a static resource that handler is a `ResourceHttpRequestHandler`, Jackson called `Resource.getContentAsByteArray()` while walking it, and every CSS, font and script request base64-encoded the file into a log line. The login page took 8–28 seconds and the heap ran out. Assets now serve in 5–25 ms.
- **`MAX_JSON_LENGTH` does not protect you.** Truncation is applied to the finished string, long after the memory has been spent. Safety has to be about what is serialised at all, never about trimming afterwards.
- **Three layers now, and each catches what the others cannot.** (a) The pointcut excludes `web.support` — infrastructure is not a business action. (b) `formatArgs`/`formatResult` use an **allowlist**: this application's own types, JDK value types and Spring Data paging are serialised, everything else is logged by class name. An allowlist because the object that broke it was one nobody had thought to exclude; a denylist would have missed it, and would still miss `Authentication` (which serialises a principal) and `Resource` (which reads the file). (c) The aspect holds a **private copy** of the ObjectMapper with a `byte[]` serialiser that writes `byte[N]` — the only thing that works at depth, because `AttachmentService.DownloadedAttachment` is an ordinary application record that happens to hold the file inside it.
- **`ResponseEntity` is summarised as `{status:…,body:…}`**, not serialised. `GET /api/attachments/{id}` returns `ResponseEntity<byte[]>` — up to 25 MB — and expanding it was the worst instance of this in the codebase. It also removes the forty mostly-null header fields that used to make every API line unreadable.
- **Before putting a new bean under any of those packages, ask what its method signatures carry.** Regression tests: `LoggingAspectTest`.

### 9c. List state across a save
- **A list page's filter, page and size live in the query string, and `redirect:/x` throws them away.** Roughly seventy redirect statements across seventeen controllers do exactly that, so every save on a filtered list used to land the operator back on page one of everything. `ListStateRedirectInterceptor` (`web/support/`) restores it in one place instead of threading three parameters through all of them.
- **Its guards are the reason it is safe to run on every web POST**, and none of them should be relaxed: only a `redirect:` view, only when the handler produced **no query string of its own** (a handler that built its own target — bulk delete does — is untouched), only when the `Referer` is same-origin and its path is **exactly** the redirect path, and `editId` is stripped or the dialog reopens on the row just saved. No `Referer` means the old behaviour, which is why a stricter referrer policy cannot break anything.
- **Do not "simplify" it by dropping the path equality check.** Without it a redirect to a detail page or to `/login` would inherit the list's query string. `ListStateRedirectInterceptorTest` has a case for each guard.
- New list pages get this for free. A new **filter** does not: add it to the paging links in `fragments/list-toolbar.html` (`classId` is there as the example) or page two silently drops it.

### 9c-2. A "skip the empty ones" predicate must agree with the code that decides what empty means
- **`form_data IS NOT NULL` is not "has values".** A log sheet is raised with one entry per asset and submitted whether or not every asset was reached, so an untouched entry holds `'{}'`. `EntrySeverityEvaluator` calls that empty and writes `max_severity` back to NULL. The startup backfill selected on `IS NOT NULL`, so it re-read the identical 3,093 rows on **every boot**, loaded their sheets, resolved their definition snapshots, stamped nothing, and logged `3093 entries stamped`. The log line was true about what it tried and false about what it achieved.
- **Two places decide "is this row done", and they have to be the same decision.** The SQL predicate now mirrors the evaluator exactly — `jsonb_typeof(form_data) = 'object' AND form_data <> '{}'::jsonb` — including the json literal `null`, which is neither SQL NULL nor `'{}'` and reaches the evaluator as a null map.
- **A drain loop needs a pass limit even when it provably terminates.** The proof is "every stamped row leaves the candidate set", which is a property of the evaluator, not of the loop. If that stops holding the application never finishes starting. `MAX_PASSES` turns it into a WARN and a boot. Regression tests: `EntrySeverityBackfillRunnerIntegrationTest` (three of its cases fail against the old predicate).

### 9c-3. Per-row INFO in a path the importer walks
- **`AssetActivationHistoryService.save` logged at INFO, once per row.** Every other importer writes a start line and a summary; the asset importer wrote one INFO line per asset because it is the only one that calls a service per row. A 10,000-row import produced 10,000 lines. It is DEBUG now — the durable record is the `asset_activation_history` row itself, and an interactive create still leaves an INFO trace through the web controller.
- **Before adding `log.info` to a service, ask whether an importer calls it in a loop.** The aspect already treats `service..*` and repository entry/exit as DEBUG for exactly this reason; an explicit `log.info` inside one of those methods opts back out of that decision.

### 9c-4. RTL mirrors ASCII parentheses — never wrap a Latin fragment in them
- **`'(' + unit + ')'` rendered as `)B(`.** Parentheses are bidi-neutral, so an RTL paragraph mirrors them; a Latin unit («B», «°C», «rpm») or a role code («ADMIN») inside them comes out backwards. This was live in `form-data-display.html`, both role pickers in `users.html`, and the parameter picker and chart labels in `asset-parameters.html`.
- **In markup, wrap the fragment in `<bdi>`** — it isolates the run and the surrounding RTL text stops reordering it. Numbers need it too: a negative reading can otherwise show its sign on the wrong side.
- **In text-only contexts (`<option>`, a canvas label), `<bdi>` is not available, so change the separator** — `label · unit`, not `label (unit)`. A single neutral character has nothing to mirror against.
- The value/unit pair reads better without the parentheses anyway: a muted, smaller unit after a space is how an instrument shows it.

### 9c-5. A font stack resolves per glyph — a named system font in it is not a fallback
- **Two identical Windows 11 machines rendered the same table differently with byte-identical CSS.** The rule counts matched the repository exactly (378 / 170 / 6), the computed colours were right, and the tables still did not match. Nothing was stale, blocked, or missing. It was font resolution, which no diff shows.
- **`'Vazirmatn Persian'` carries a `unicode-range` covering only Persian/Arabic**, so every Latin glyph fell through to the next stack entry — which was `'Segoe UI'`. Asset codes, ids, tag numbers and every chart axis were drawn by the operator's copy of Windows. This is the big one, and it read as a courtesy fallback.
- **Bootstrap styles every `<code>`, `<kbd>`, `<pre>` and `<samp>` from `--bs-font-monospace`**, whose default is a pure system stack (SFMono-Regular, Menlo, Monaco, Consolas, Liberation Mono, Courier New). About thirty `<code>` elements live in the panel's tables. Removing our own declarations would not have touched them; the variable has to be overridden.
- **The generic `monospace` keyword is a per-browser setting** (chrome://settings/fonts), so it varies between identical installations. Legal as the *last* entry of a stack, never as the first — behind a font we serve it is unreachable, in front of one it is the whole declaration.
- **Use `var(--app-font-sans)` / `var(--app-font-mono)`.** Both end at Vazirmatn, which is served from `static/fonts/vazirmatn/`. Vazirmatn is not monospace, so codes are set apart by the pill background, weight, `letter-spacing` and `font-variant-numeric: tabular-nums` instead of by the face.
- `CssHasNoSystemFontsTest` fails the build on any named system font, any stack starting at a generic keyword, a missing `--bs-font-monospace` override, or a `@font-face` pointing at a URL rather than a file in this repository. The PWA has the same guard in `src/theme/noSystemFonts.test.ts`.

### 9d. Page size is a shared constant, and a second pager needs a second parameter
- **`WebListSupport.PAGE_SIZES` (25 / 50 / 100 / 250) and `MAX_SIZE` are the single source.** The size selector in `fragments/list-toolbar.html` and in each report template renders from the constant, so the offered options can never drift from what the server accepts. Do not hard-code an `<option>` list; a page offering 500 while `clampSize` caps at 250 silently ignores the operator.
- **`clampSize` must run before any early return.** `assetsWithoutRecentReadingsPage` clamped after its no-access short-circuit, so `?size=100000` on a scope-less account built a `PageRequest` of 100000. Clamp first, return second.
- **A page with two lists needs two page parameters.** کیفیت داده pages سلامت تگ‌های NFC with `nfcPage` and دارایی‌های بدون قرائت with `page`, and each pager's links carry the other's current value. Sharing one number moves both sections at once and the operator loses their place in the queue they were not looking at.

### 10. API documentation (OpenAPI — admin only)
- `springdoc-openapi` (`OpenApiConfig.java`) documents `/api/**` only, generated automatically from `@RestController` classes — a new mobile endpoint needs **no manual step** to appear (unlike permissions, which do).
- Enabled in every environment, including production (`springdoc.api-docs.enabled` / `springdoc.swagger-ui.enabled=true` in `application.properties`). Access is gated behind `GET:/v3/api-docs/**` (`PermissionCodes.GET_API_DOCS`, seeded in `V1__initial_schema.sql` — folded in from the original `V4__ops_monitoring_permissions.sql`, see §2 — `ADMIN` only) via `WebSecurityConfig` — same pattern as Actuator (§ above). Do not make the spec/UI `permitAll()`.
- Do not widen `springdoc.paths-to-match` to include the Thymeleaf `web/` panel; it isn't a machine-consumed API.

## Gotchas checklist

1. Unique-constraint updates → validate detached candidate before dirtying managed entity.
2. Hierarchy cascade uses persisted ancestry (`FlushMode.COMMIT`) — pass prior IDs when entity already mutated in memory.
3. Large reparent = expensive single TX — treat as maintenance.
4. Bootstrap ≠ full master catalog; use log-sheet bundles for assets/fields.
5. Inactive assets: NFC yes, generation/preview **and custom-sheet selection** no.
6. One sub-function → one asset (DB + service + import).
7. User hard-delete blocked after app activity — prefer deactivate.
8. Import files live under `./data/imports` (runtime; often gitignored via `data/`) — TRUNCATE jobs does **not** delete disk files.
9. Permission matrix in Flyway + service-layer gates both matter; **never add a new authority without a Flyway permission insert** (reuse parent authorities for export/options/draft when appropriate).
10. Custom sheets: no template scope walk — asset set is explicit; do not assume one `classId` per sheet when reading snapshot/bundle.
11. `VOIDED` ≠ `CANCELLED` and ≠ `log_sheet_void_submissions` (late superseded sync). Parameter reports filter `status = SUBMITTED` only — voiding excludes readings automatically.
12. A signed JWT is no longer sufficient — its `jti` must map to a live `api_sessions` row. Issuing a token outside `AuthApiController` without calling `ApiSessionService.register` produces a token the filter rejects.
13. Never bind a nullable `String` into a JPQL `LOWER(...)` comparison: PostgreSQL infers `bytea` and fails with `function lower(bytea) does not exist`. Write a separate termless query (see `ApiSessionRepository.findActive`).
14. Field keys must not contain `.`, `[`, or `]` (`MasterDataUniquenessValidator`) — the PWA uses them verbatim as react-hook-form names, where those characters mean nested paths.
15. Do not commit unless the user asks; do not push unless asked.
16. A `permitAll()` route for a URL with **no registered MVC handler** (e.g. a conditionally-disabled feature) still redirects an anonymous caller to `/login` instead of 404ing — Spring Security re-authorizes the internal `/error` forward that `DispatcherServlet` triggers on 404, and `/error` isn't in the permit list. This is identical to hitting any other dead URL while unauthenticated; it does **not** mean the `permitAll()` rule failed. Don't "fix" it by adding `/error` to permitAll or chasing it as a bug.
17. `HttpSecurity.authenticationProvider(provider)` (used on the web chain) is **not** the same as passing an explicit `AuthenticationManager` — it lets `HttpSecurity`'s internal builder silently attach the Boot-auto-configured *global* `AuthenticationManager` as a **parent**, and that global manager also resolves to the very same `@Component`-registered provider. Net effect: on a failed login, `additionalAuthenticationChecks()` runs **twice** (once locally, once via parent fallback after the first throws) — e.g. `LoginAttemptService.recordFailure` double-counting every wrong password from the web form only, not from `/api/auth/login`. Fix/pattern: build one explicit no-parent `AuthenticationManager` bean (`new ProviderManager(provider)`) and wire it into **every** chain via `.authenticationManager(...)`, never `.authenticationProvider(...)`, so both entry points share the exact same single-invocation instance (see `WebSecurityConfig`).
18. A raw JS array-of-arrays literal (`[[...]]`) — or anything else starting with two adjacent `[`/`(` — inside a Thymeleaf-processed `<script>` block gets misread as Thymeleaf's own **inline expression** syntax (`[[${...}]]` / `[(${...})]`) and fails template parsing with a cryptic `attoparser.ParseException: Could not parse as expression`. This breaks the **whole page** (500, and in a real browser often surfaces as a stuck/looping `net::ERR_INCOMPLETE_CHUNKED_ENCODING` load, not an obvious error). Add `th:inline="none"` to any `<script>` tag whose JS wasn't written with Thymeleaf inlining in mind (see `field-definitions.html`). Also: editing a `.html` template while the app is already running via `spring-boot:run` does **not** reliably hot-reload it — restart to pick up template changes before trusting a browser test.
19. User-submitted deadline/schedule dates go through `DateUtils.requireFutureWithinYears(epochMs, now, label)` (must be strictly future, at most `MAX_FUTURE_YEARS` ahead) — see [README § User-submitted date validation](README.md#user-submitted-date-validation) for the full call-site list. On `LogSheetTemplateService.update`, only re-validate `scheduleStartAt` when it **actually changed** from the persisted entity (`!Objects.equals(existing, form)`) — a live template's original start naturally drifts into the past as its schedule keeps running, so unconditionally re-checking it would block unrelated edits (e.g. a rename) with a spurious "must be in the future" error. When adding a new user-facing date field, reuse this helper rather than a bespoke `<= now` check, and add it to the README table.
20. **Reassigning a partially-completed log sheet leaks the previous operator's readings into the new operator's view, silently.** Nothing in the reassignment path touches `log_sheet_entries` — `LogSheetAssignmentService.reopenSubmittedWithExtend` (preserves entry form data by design, only resets sheet-level timestamps) and `assign`/`reassign` (bulk `UPDATE LogSheet SET ...` JPQL, `LogSheetRepository.assignIfPending`/`reassignIfStillOpen` — cannot touch another table) never modify entries. `FormDataValidationSupport.validateFilledEntry` explicitly allows a completely blank entry to pass validation, so a 3-of-10-filled submission is accepted as a normal `SUBMITTED` outcome — this isn't a bug, partial submission is intentional. The mobile bundle endpoint (`LogSheetBundleService.buildFullBundle` → `LogSheetEntryRepository.findByLogSheetId`, no assignee/requester filter) always returns each entry's *current* `formData` regardless of who's asking. On the PWA, a device that has never seen the sheet locally before (`applyLogSheetBundle` in `logSheetSync.ts`, `existing` branch is falsy) copies `bundle.entries` straight into the new local record — `mergeEntriesPreservingFormData`/`mapServerEntryToLocal` in `mergeLogSheetBundle.ts` always fall back to `serverForm` when there's no matching local entry, since `preserveLocal` only matters when local data exists. Net effect: submit 3-of-10 → supervisor reopens (`reopenSubmittedWithExtend`) → reassign to a different operator → the new operator sees the first 3 assets pre-filled from the DB and, if they don't touch those rows, ends up submitting the first operator's readings under their own `completedByUserId`/`operatorName`. **Partial progress**: `log_sheet_entries.filled_by_user_id` / `entry_source` (added directly in `V1__initial_schema.sql`, originally shipped as a standalone `V2__nfc_fault_reports.sql` before being folded back in, see §2) now record who actually filled each individual entry and how — the display gap is closed (`log-sheet-detail.html`'s entries table shows both columns). The underlying formData leak itself (new assignee's device silently inherits the previous operator's readings) is **still unchanged** — that part is still flagged for a future decision (e.g. resetting or flagging entries on reassignment). What **is** fixed: `mergeMobileEntryUpdates` / `applyWebEntryValues` no longer blindly re-stamp `entry_source`/`filled_by_user_id` on every submit just because an entry "has data" — a mobile submit always resends *every* entry currently on the device (including ones the submitter never opened), so unconditional stamping meant a second operator's resubmit of an untouched, already-filled asset silently reassigned it to themselves and, since their own device never locally knew it had been filled manually, downgraded a fault-report-driven `PWA_MANUAL` entry to `PWA_NFC`. Reproduced live on log sheet #8 (operator1 fault-reported + manually filled 2 assets and submitted; supervisor reopened, took over, reassigned to operator2; operator2 filled their own 2 assets and resubmitted — one of operator1's untouched assets flipped from `PWA_MANUAL`/operator1 to `PWA_NFC`/operator2). Fix: both methods now compare the incoming `formData` against the entry's *currently stored* `formData` (`Objects.equals`) and only re-stamp attribution when it actually changed — an unchanged resend leaves the original author's `entry_source`/`filled_by_user_id` untouched. Tests: `submitPreservesOriginalAttributionWhenResubmittingUnchangedEntry`, `submitReattributesEntryWhenDataActuallyChanges`, `webDraftSavePreservesOriginalAttributionWhenValuesUnchanged` in `LogSheetServiceTest`.
22. **A `role_permissions` blanket grant (`SELECT ... FROM roles r CROSS JOIN permissions p WHERE r.code = 'ADMIN'`, no code filter) only covers permission rows that exist in the table *at the moment that INSERT statement itself runs*.** It is not a live rule re-evaluated later — it's a one-time snapshot. This is harmless when the blanket grant and the new permission rows are both in the *same* migration file (the new rows exist by the time the blanket-grant statement executes further down the same script) — the case exercised earlier when V1-V5 were consolidated into a single `V1__initial_schema.sql`. It silently fails when a *later*, separate migration (e.g. the original standalone `V2__nfc_fault_reports.sql`, before it got folded back into V1 — see §2) adds new permission rows and assumes V1's already-applied ADMIN/HIGH_USER blanket grants will "automatically" cover them — V1's grant statement executed and finished long before V2 ever ran, so ADMIN ends up **without** the new permissions despite `SecurityUtils.isAdmin()` being true, and no test catches it: `EndpointSecurityTest`'s `@WithAppUser(authorities = "...")` injects the authority string directly into the mock principal, bypassing the real `roles`/`role_permissions` join entirely, and Mockito-based service tests don't touch the DB at all. This was only caught by a live app boot + real admin login + real page hit — the standard verification step, not an edge case. Fix: **every separate migration file** after V1 must **explicitly** `INSERT INTO role_permissions` for ADMIN (and HIGH_USER, for non-admin-category rows) for its own new permissions — this stops being necessary once folded back into V1 itself, since the blanket grant then naturally runs after the new permission rows in the same script (verified: after folding the NFC-fault-report permissions into V1, `ADMIN`'s `role_permissions` row count exactly equals the total `permissions` row count, with **zero** duplicate-key errors from also keeping old explicit per-role grants — those must be **dropped**, not kept, once folded, since the blanket would try to insert the same `(role_id, permission_id)` pair a second time and violate the composite PK). Roles without a blanket grant (`SUPERVISOR`/`OPERATOR`/`SENIOR_OPERATOR`, which use explicit `IN (...)` lists) still need their own explicit grants regardless of fold state.
23. `RecurrenceUnit` includes `MINUTE` (added for sub-hourly template schedules, e.g. every 20 minutes) alongside `HOUR`/`DAY`/`WEEK`/`MONTH` — plain `VARCHAR(20)` column, no Flyway migration needed for new enum values. `LogSheetTemplateService.scheduleOverlapRisk(form)` is a **non-blocking, informational-only** check: when the completion window is longer than the recurrence interval, the previous occurrence(s) are still open when the next one generates, so open sheets for the same assets can stack up. It deliberately never blocks create/update (product decision) — the web controller surfaces it as a `warningMessage` flash attribute (new alert block in `fragments/layout.html`, alongside the existing `successMessage`/`errorMessage`) shown *together with* the success message, not instead of it. `recurrenceIntervalMinutes` approximates MONTH as 30 days on purpose — this only feeds a heads-up, not validation, so exact calendar math isn't needed. The scheduler's own poll interval (`app.scheduler.log-sheet-gen-ms`, default 60s) is unrelated to this check and still has ample margin at 20-minute granularity; nothing enforces a minimum `recurrenceEvery` for `MINUTE`, so a very small value (e.g. 1) is accepted without warning about poll-interval margin specifically.
24. **`asset_entries.status`** (`VARCHAR(30)`, nullable — added directly in `V1__initial_schema.sql`, originally shipped as a standalone `V3__asset_status_field.sql` before being folded back in, see §2) is a schema-only field for the asset's real-world operational state (ON / OFF / IDLE / MAINTENANCE, etc.) — explicitly requested as DB-only for now, with no entity field, DTO, API, or UI wiring yet. This is safe: `spring.jpa.hibernate.ddl-auto=validate` only checks that entity-mapped columns exist in the schema, not that every schema column has a mapped entity field, so an unmapped extra column never breaks startup. Deliberately left without a CHECK constraint or backing Java enum, unlike `NfcFaultReportStatus` — the exact set of states hasn't been decided, and constraining it now would just mean loosening it again later (see `NfcFaultReportStatus`'s own migration comment for the same reasoning pattern). Not the same concept as the existing `active` boolean, which only gates log-sheet template preview/generation, not real-world operational state. When this is actually wired up: add `AssetEntry.status` with `@Column(name = "status")`, then DTO/mapper/UI as needed — no new migration required for that follow-up.
25. **`users.national_code` / `phone_number` / `nfc_tag_id` are now unique-or-blank** (`ux_users_national_code`, `ux_users_phone_number`, `ux_users_nfc_tag_id_lower` — added directly in `V1__initial_schema.sql`, originally shipped as a standalone `V4__user_contact_field_uniqueness.sql` before being folded back in, see §2) — previously these three optional contact fields had zero uniqueness enforcement, so two users could silently share the same national code, phone number, or NFC badge tag. Plain (non-partial) Postgres unique indexes were used, matching the existing `ux_asset_entries_nfc_tag_id_lower` pattern exactly — standard unique indexes already permit unlimited `NULL` rows (NULL is never equal to NULL), so no `WHERE x IS NOT NULL` partial-index trick is needed. `nfc_tag_id` is case-insensitive (`LOWER(...)`, same reasoning as the asset one — it's the same kind of value); `national_code`/`phone_number` are plain since they're digit strings. App-level pre-checks were added in `UserService.applyContactFields()` (mirrors the existing `existsByUsername` duplicate check, using `user.getId()` for self-exclusion on update — works for both create and update since `user` is either a fresh unsaved entity with `id == null` or the already-`findById`-fetched managed entity) so admins get a friendly Persian message (`ErrorTranslator`: `"Duplicate national code:"` / `"Duplicate phone number:"` / reuses the existing `"Duplicate NFC tag:"`) instead of a raw constraint violation — the DB constraint itself is still the source of truth and has a matching `ErrorTranslator.constraintSpecificMessage` entry as a backstop for races. Tests: `UserServiceTest` (`createRejectsDuplicateNationalCode`, `createRejectsDuplicatePhoneNumber`, `createRejectsDuplicateNfcTagCaseInsensitive`, `updateAllowsKeepingOwnContactFieldValues`, `updateRejectsContactFieldOwnedByAnotherUser`).
26. **A location is owned by MANY operational units (`location_units`), not one.** There is no `locations.unit_id` column — it was replaced by a composite-PK join table with the same shape as `unit_supervisors`/`unit_operators`. Everything that resolves unit scope starts there: `AssetUnitScopeSql.SCOPED_SUBFUNCTIONS_CTE` (its `loc_roots` CTE selects from `location_units`) and `LocationRepository.findIdsByUnitIdIn` (JPQL over `LocationUnit`). When adding a scope query go through one of those two — never re-derive ownership from `Location`, which no longer carries it. Write paths must rewrite the links wholesale via `AssetHierarchyService.saveLocation(loc, unitIds)` / `replaceLocationUnits` (delete-then-insert, de-duplicated: the composite PK rejects a repeated pair coming from a multi-select). The unit delete-guard moved from `LocationRepository.existsByUnitId` to `LocationUnitRepository.existsByUnitId`. Display reads use `unitIdsByLocationId`, which deliberately returns an entry for **every** requested id (empty list when unowned) so Thymeleaf never has to null-check a lookup — see gotcha #18 for why one bad template expression takes the whole page down. Excel import/export carry a comma-separated `unitCodes` cell (the importer also accepts the Persian comma).
27. **`log_sheet_templates.restrict_scope_to_unit` is a scope-PICKING rule, never an access rule.** With it off, the scope may point anywhere in the plant so a unit can be made responsible for assets outside its own locations, and the `scopeBelongsToOperationalUnit` validation is skipped. Access is completely unaffected: a log sheet is reachable only through `log_sheets.operational_unit_id` (`LogSheetAccessService.canView` / `findAvailablePool` / `findTeamOpenForSupervisor`), and `LogSheetBundleService` returns the sheet's entries **without** re-filtering them by asset unit scope — which is precisely what makes out-of-unit assets fillable. Do not "fix" that by adding an asset-scope filter to the bundle; it would break this feature. The privilege-escalation guard is that only non-unit-scoped roles may clear the flag: `LogSheetTemplateService.applyScopeRestrictionPolicy` forces it back to `true` for a unit-scoped supervisor (the flag arrives as a plain form field, so a UI-only check would be bypassable), and `LogSheetTemplateWebController.allowUnrestrictedScope` mirrors that on the option endpoints so the pickers cannot be coaxed into listing another unit's hierarchy. Reports and master-data lists stay location-unit scoped (`AssetAccessService`) and are intentionally *not* widened by this flag. Tests: `LogSheetTemplateServiceTest` (`createAllowsScopeOutsideUnitWhenRestrictionIsOff`, `unitScopedSupervisorCannotDisableTheScopeRestriction`, `adminMayUnrestrictScopeButUnitScopedUserMayNot`) and `AssetUnitScopeQueryIntegrationTest.locationSharedByTwoUnitsIsVisibleToBoth`.

28. **A log-sheet template has TWO asset-selection modes and they must not be blurred together** (`log_sheet_templates.asset_selection_mode`, `SCOPE` | `EXPLICIT`, default `SCOPE`). `SCOPE` is the historical behaviour: every generation re-runs the hierarchy walk ∩ `class_id`, so an asset added to that scope later **automatically joins** the next sheet. `EXPLICIT` is the scheduled counterpart of a custom log sheet: the asset set is **frozen** in `log_sheet_template_assets` and must reproduce identically on every run — the *only* way an asset leaves it is being deactivated (`active = false`), and because the membership row survives, re-activating brings it back with no re-edit. Do not "helpfully" re-resolve an EXPLICIT template from its scope, and do not prune membership rows when an asset goes inactive — both would silently destroy the guarantee the mode exists for. An EXPLICIT template stores `scope_type`/`scope_id`/`class_id` as **NULL** (`class_id` had to be made nullable), so anything reading those three must tolerate null: `buildScopeSummary` returns null (a scope string would misrepresent a hand-picked set — same as `CustomLogSheetService`, which has always written null there), and display goes through `ReferenceLabelService.templateAssetSourceLabel(mode, ...)` rather than `templateScopeDisplayLabel`, which would render a bare «—». Its assets **may span several classes**, so the field-definition snapshot uses the multi-class `captureSnapshot(Set<Long>)` overload, never the single-class one. `resolveExplicitAssets` preserves the author's chosen order (map-by-id over the saved id list, not the query's return order). Access control mirrors gotcha #27 exactly: `LogSheetTemplateService.validateExplicitAssets` confines a unit-scoped supervisor to `findVisibleActiveByIdInAndUnitIds` while plant-wide roles get `findActiveByIdIn`, and `LogSheetTemplateWebController.assetOptions` reuses the same `allowUnrestrictedScope` guard — the ids arrive as plain form fields, so a UI-only check would be bypassable. `fk_lsta_asset` is `RESTRICT`, so `MasterDataDeleteService.assertDeletableAssetEntry` needs its own explicit guard (with an `ErrorTranslator` entry) or the user gets a raw constraint violation instead of a Persian message. In the form, EXPLICIT mode **disables** the scope/class inputs rather than just hiding them, so the browser neither enforces their `required` nor submits stale values. **No PWA change is needed** for any of this — a null `scope_summary` and multi-class entries are the exact shape custom log sheets have always produced, and the PWA already normalizes `scopeSummary ?? ''` and resolves field definitions per-entry class. Tests: `ExplicitTemplateAssetIntegrationTest` (frozen vs dynamic side-by-side, deactivate/reactivate, multi-class, delete guard), plus the `explicit*` cases in `LogSheetGenerationServiceTest` and `LogSheetTemplateServiceTest`.
29. **A sub-function is a SLOT, not a piece of equipment: one ACTIVE asset, unlimited INACTIVE ones.** `ux_asset_entries_sub_function_id` was replaced by the **partial** index `ux_asset_entries_active_sub_function ON asset_entries (sub_function_id) WHERE active`, because replacing a broken pump means deactivating it (kept for history, still attached to the same sub-function) and attaching its successor to that same slot. 48. **`log_sheet_entries.max_severity` / `breached_fields` are denormalised, and the only safe place to compute them is the write.** Severity is not a SQL predicate — the value lives in `form_data` (jsonb) and its thresholds live in *another row's* `validation` json — so "which assets are out of range" used to mean opening every candidate sheet and evaluating in Java, capped at 500 sheets. Fine for a person opening a page, useless for a job polling every few minutes. `EntrySeverityEvaluator.apply(entry, fieldDefs)` now stamps the verdict at save time and the exception report is one indexed query (`idx_log_sheet_entries_breaches`, partial on WARNING/DANGER). **Every path that mutates `form_data` must call it immediately after `setFormData(...)`** — today exactly two: `LogSheetService.mergeMobileEntryUpdates` (mobile batch) and `applyWebEntryValues` (web draft save *and* web completion, which share it). Call it on **every** write, not only when the value changed: a resubmit, a correction and a clear all have to leave the flag agreeing with what is stored. A path that skips it leaves a stale flag, which is worse than no flag because it reads as authoritative — `EntrySeverityPersistenceIntegrationTest`'s correction/downgrade/clear cases are the tripwire. Three encoding decisions matter: `NULL` means *never evaluated or no values* and is deliberately distinct from `'OK'` (evaluated and clean), so pre-existing rows are invisible rather than falsely clean; `breached_fields` lists danger keys before warning keys so a reader needs only one column; and definitions are resolved through `LogSheetFieldDefinitionsService`, which prefers the sheet's `field_definitions_snapshot`, so re-tuning a range never re-judges history. Anything reading `log_sheets` stays cheap forever (~3,650 rows/year). The exception report does **not** degrade because `idx_log_sheet_entries_breaches` is *partial* — it indexes only WARNING/DANGER rows, which are a small minority, so it stays small however big the table gets; that is what makes it safe for an external system to poll. The two full-scan aggregates (`entrySourceSplitByUnit`, `lastSubmittedReadingPerAsset`) grow linearly with entry count — ~0.35 s at 5 years, ~0.7 s at 10 — and the fix when they matter is a nightly rollup table, **not** more indexes, since they aggregate over every row in the window. Two bugs the measurement exposed: `overview()` used to derive its danger/warning figures by fetching `outOfRangeReadings(...)` and counting the list, which was silently capped by the page limit, so any period busier than the cap under-reported — it now counts in SQL via `countBreachesBySeverity`; and `openNfcFaults()` called `findAll()` and filtered in Java, now `findOpenForUnits(unitIds)`. Known, documented limit: `assetsWithoutRecentReadings` inspects `limit * 4` assets, which is every asset at hundreds but a sample at tens of thousands.

50. **`RoleService.duplicateRole` copies permissions only, and never the `systemRole` flag.** It delegates to `createRole` so the duplicate-code check and `systemRole = false` live in exactly one place. Copying the flag would create a second undeletable role; copying user assignments would grant the new role to everyone who held the original, which is the opposite of what an administrator building a narrower variant wants — `duplicateDoesNotCopyUserAssignments` pins that with `verifyNoInteractions(userRoleRepository)`. A blank description inherits the source's (blank means "not supplied", not "deliberately empty"). The web form is **one shared modal** whose `th:action` is a placeholder (`/roles/0/duplicate`) retargeted by JS to the clicked row — one modal instead of N in the DOM, and Thymeleaf still injects the CSRF hidden field because the element is a `th:action` form. Note the web chain **has CSRF enabled** (only the `/api/**` chain disables it), so any curl-based test of a web form must pull `_csrf` from the rendered page first.

51. **An asset's `status` moves only when a supervisor approves a request — completing a sheet merely proposes.** A completed sheet whose class field keyed `status` (case-insensitive) differs from the asset's current value raises a `PENDING` row in `asset_status_change_requests`; `AssetStatusRequestService.decide` is the only path that writes the column, via `AssetStatusService.writeStatus`. Equal or blank readings raise nothing (blank means "not recorded", not "no state"). **The only-latest rule is the load-bearing part:** any decision that would move the column — approving, or undoing an approval back to PENDING/REJECTED — is refused unless the request is that asset's newest, because an undo restores `applied_old_status` and doing that to a middle request would roll the asset back over decisions taken since. Rejecting a *pending* request is always allowed, since it changes nothing. Undo is exact because the value replaced is **stored at approval time** rather than re-derived. **Do not add a second mechanism:** void/reopen/restore deliberately no longer touch asset status, and the asset form's status field is read-only after creation with the service ignoring it — with two writers the only-latest rule could be broken by the sheet lifecycle itself, silently. Every history row carries `request_id` so the timeline says which decision produced it. `AssetStatusIntegrationTest` (23 cases) pins all of it, including a forged-POST equivalent.

52. **A `<script>` or pager placed after `</div>` of `#pageContent` is silently dropped — it renders nothing and reports no error.** Every admin page declares `th:replace="~{fragments/layout :: layout(~{::title}, ~{::#pageContent})}"`, so the layout copies **only** those two nodes. Markup outside `#pageContent` simply never reaches the browser. This bit twice in one change: the voided-submission filter's script tag and the breach report's whole pagination `<nav>` both sat after the closing div, so both features were fully dead in the browser while every unit test passed and the page looked superficially fine. Neither a compile nor a template-render error appears — the only way to catch it is to open the page. Put page-level scripts and any trailing markup **inside** `#pageContent`, as `log-sheet-detail.html` and `operational-units.html` already do.

53. **"Has rows" is not "has data" once a field can be legitimately empty.** `LogSheetVoidSubmissionViewService.VoidedEntryRow.hasData()` used to be `!fields.isEmpty()`, which filed a card whose every parameter renders «ثبت نشده» under *دارای داده* — precisely the distinction the with/without-data filter exists to draw. It now asks whether any field is non-empty, reusing `FormFieldRow.isEmpty()`. The case that exposed it was a multiselect submitted with nothing chosen: the row exists, the value does not. The same principle drives the display layer — an unfilled row used to render as its bare unit («°C» and nothing else), indistinguishable at a glance from a filled one.

54. **`asset_entries.active` and `asset_entries.status` are journalled in two separate tables, and merging them would break log-sheet reversal.** They look alike and are not: `status` is a reading about the equipment that a sheet sets and a reversal takes back, while `active` is a registry decision — whether the record takes part in generation — that no sheet ever touches. `AssetActivationHistoryService` writes to `asset_activation_history` (`CREATED` / `ACTIVATED` / `DEACTIVATED`, with `was_active` NULL only on the creation row); `AssetStatusService` writes to `asset_status_history`. The temptation is to fold activation into the status table behind a `kind` column — **don't**: `findActiveAppliedForSheet` selects unreverted `APPLIED` rows for a sheet, and one mis-scoped query there would make voiding a log sheet switch assets on and off. Separate tables make that impossible rather than merely unlikely; they are merged only in `AssetHistoryViewService`, which is display and cannot reach back into behaviour. `AssetHistoryIntegrationTest` pins the independence in both directions. A manual status edit goes through `AssetStatusService.applyManualChange` (`source = MANUAL`) rather than a plain setter — and note it **mutates the entity without saving**, because `AssetEntryService.update` saves once at the end. Blank means opposite things on the two paths and that is deliberate: ignored from a sheet ("not recorded"), applied from the form ("no known state"). Every asset-creating path must write the baseline activation row — `AssetEntryService.create` and the Excel import both do; the async batch import has no security context, so its actor is null and renders as «سیستم».

55. **Thymeleaf reads the strings `"off"`, `"false"` and `"no"` as boolean FALSE, so `th:if="${someString}"` silently hides exactly those values.** An asset status of literally `OFF` — one of the three options in the live data — rendered as «ثبت نشده» on three separate pages before this was spotted, and only by opening them: the templates compiled, the tests passed, and the value was simply absent. Use `th:if="${!#strings.isEmpty(x)}"` / `th:if="${#strings.isEmpty(x)}"` for any string that a user supplies or a class field defines, never truthiness, and never `th:unless` paired with a truthy `th:if` (both branches then agree it is false and you get neither). `AssetHistoryPageIntegrationTest` asserts the rendered HTML contains `OFF` as the regression guard.

56. **`Map.of()` is immutable and its `get(null)` throws `NullPointerException`.** `AssetHistoryViewService` builds lookup maps for actor names and sheet titles and returns `Map.of()` when there is nothing to look up; a history row with a null `actor_user_id` — which is normal, since the async Excel import runs with no security context — then took the whole page down with an NPE that surfaced as a redirect to `/`, not as an error anyone would recognise. The fix is a null-guarded `nameOf(map, id)` helper rather than a guard at each call site, so a future field cannot reintroduce it. Prefer `HashMap` or an explicit null check whenever a map's keys can be null.

57. **"Appeared on a submitted sheet" is not "was read", and two reports got that wrong in opposite directions.** A log sheet is raised with one entry per asset and submitted whether or not the operator reached every asset, so untouched entries are the majority — 128 of 133 rows on the first live dataset. The manual-vs-scanned split divided by *every* entry (a unit with 94 entries of which 3 held a reading showed an all-manual round as 2%), and silent-asset detection treated an untouched entry as a reading, reporting **zero** silent assets while 46 active assets had never been read. Both now filter on **`max_severity IS NOT NULL`**, which is exactly "form data is non-empty": `EntrySeverityEvaluator.apply` nulls the column when form data is null/empty and always writes at least `OK` otherwise, on every write path (gotcha #48), with `EntrySeverityBackfillRunner` covering legacy rows — verified against live data with zero disagreement either way. `idx_log_sheet_entries_asset_read` is partial on that predicate so the per-asset lookup reads only rows that can answer the question. When you add a report over entries, decide explicitly whether it counts *assets scheduled* or *readings taken*; they are different numbers and the difference is usually most of the rows. `DataQualityReportIntegrationTest` pins both.

58. **A report that samples then filters is not just slow, it is wrong.** `assetsWithoutRecentReadings` used to fetch `limit * 4` assets and filter them in Java. Past a few hundred assets that stops being "the plant's worst offenders" and becomes "whatever slice the paging query returned" — a ranking computed over a sample is not a ranking. It is now one scoped SQL statement that orders and limits where the whole set is visible (`findSilentAssets`, plus `findSilentAssetsUnrestricted` for admins). Note the split: the scoped query is built on a recursive CTE binding `:unitIds`, and SQL cannot express "every unit" through that binding — passing null silently matches **nothing**, which is how the whole section came back empty for an admin. `findReportableAssets` splits the same way for the same reason; `visibleUnitIds()` returning null means unrestricted and always needs its own branch.

59. **`enhanceTables()` decorates every `#pageContent table.table`, including nested ones — and its `min-width: max-content` breaks them.** The enterprise treatment (sticky headers, density controls, column toggles, scrolling viewport) is meant for data grids. Applied to the per-asset parameter table nested inside a log-sheet cell, the min-width let that table grow past the cell holding it, so an asset with three photos had its third tile pushed outside the visible box. `enhanceTables` now skips anything inside `.form-data-table`, and `app.css` pins `min-width: 0 !important; table-layout: fixed` on those tables as a second line of defence. Opt out by **structure**, not by a per-table flag, so the next nested table is safe the day it is written.

60. **Schema changes go in a NEW versioned migration from V2 onward — do not edit V1 again.** V1 is the established baseline and has been applied to live databases; editing it changes its checksum and forces the manual realignment dance (boot, read "Resolved locally", `UPDATE flyway_schema_history SET checksum = …`, boot again). A new `V2__*.sql` is applied by Flyway on the next boot with no intervention at all — which is exactly what happened for `asset_status_change_requests.reading_recorded_at`. Keep each migration to one coherent change and say in a header comment why the column exists, not just what it is.

61. **An asset status change is dated to when the reading was TAKEN, not when it was approved.** `reading_recorded_at` on the request carries the log sheet entry's device timestamp (`updatedAt`, falling back to `createdAt`), and approval passes it to `AssetStatusService.writeStatus` as the history row's `changedAt`. Without this every asset's timeline bunches up around review times and stops lining up with the rounds that produced it — a status seen at 08:15 and signed off at 16:40 belongs at 08:15. **Undo is deliberately dated now**: it is an administrative decision, not an observation, and back-dating it would hide when the correction happened. The asset row's `updated_at` also stays real time — only the history entry moves, because that is the thing being described. A manual request uses its filing time; a request predating the column falls back to `requestedAt`.

62. **A manual status request needs the asset's class to declare a `status` field, and the picker must share the save's scope.** `statusOptionsForAsset` resolves the field from the class as it stands *today* (unlike a sheet-raised request, which reads the sheet's frozen snapshot) and returns its declared options; `raiseManual` refuses outright when there is no such field, and refuses an off-list value when the field declares options. The asset picker endpoint uses `findReportableAssets` — the same scope `raiseManual` validates with — so the list can never offer something the save would then reject; pairing a wider picker with a narrower validator is the bug this avoids. The form asks for the asset first because a status is only meaningful in that class's vocabulary.
63. **The web form posts a `location` field as TWO same-named inputs, and they must be paired before validation runs.** The browser submits same-named controls in document order, so the server receives `[lat, lng]` and `LocationValues.fromWebPair` turns that into the canonical `{type,lat,lng}` object — the same shape the PWA's GPS capture sends, so no reader ever has to cope with two shapes. `normaliseWebEntryValues` runs at the **entry points** (`completeFromWeb`, `saveDraftFromWeb`) rather than inside `applyWebEntryValues`, because validation reads the submitted map directly: normalising afterwards meant every location field on the sheet — including the empty ones — failed as "not a valid lat/lng" and no sheet with a location field could be submitted at all. A pair that will not parse is dropped, not stored, so the field reads as unanswered rather than as half a position.

64. **The PWA captures location, the web panel types it, and that asymmetry is the design.** On a device there is a real position to read, so `LocationFieldInput` offers capture only — a typed coordinate there would be an unverifiable claim about where somebody stood. In the panel there is no device, so a supervisor enters the numbers. `captureCurrentLocation` uses `enableHighAccuracy` with `maximumAge: 0` (a cached or network fix cannot tell one pump from the next) and keeps `accuracy`, because a plant fix can be tens of metres out. Required-ness is checked with `parseCoordinate`, not `required`: the value is an object, and an object is truthy even when it holds nothing usable — the same trap as the media fields.

65. **An NFC scan failure must not describe the mechanism.** Missing Record 1, a serial that does not match, and an asset with no serial recorded all show one message (`nfcVerificationFailed`). The old text named which check failed — "the chip serial does not match", "no serial is recorded for this asset" — which hands whoever is holding the tag a map of how verification works, and the operator's next step is identical in all three cases anyway. The one failure that stays specific is a *valid* tag that is simply not on this sheet: that is a routing mistake the operator can act on and it reveals nothing. Keep this distinction if you add outcomes to `matchLogSheetEntryByTag`.

66. **`screen.orientation.lock()` fails for reasons that are not the operator's problem, so every failure is swallowed.** Desktop browsers have no orientation, iOS Safari has no `lock`, and Chrome rejects outside an installed PWA — all of which mean "this device rotates freely", which is exactly the Auto behaviour. `applyScreenOrientation` returns false rather than throwing, and the Settings screen says once, quietly, when the browser cannot lock. The preference is stored in local settings and never syncs: it depends on how that particular tablet is mounted, so a shared account must not drag one device's choice onto another. It is re-applied on every launch from `App` because a lock does not survive the app closing.
67. **A null map key in a Thymeleaf expression fails in SpEL, before the map is ever consulted.** `${userNameById[r.requestedByUserId]} ?: 'سیستم'` looks safe and is not: SpEL's `Indexer` throws `IllegalStateException: No index` on a null index, so neither the map's implementation nor the elvis operator gets a say. This is a *different* failure from #56 — that one is `Map.of().get(null)` in Java, and swapping in a `HashMap` fixes it; this one is not fixable from the controller at all. Write the guard in the template: `${id == null ? 'سیستم' : (map[id] ?: 'سیستم')}`. Note also that `th:if` (precedence 300) is evaluated **before** `th:with` (400), which is why `th:if="${r.logSheetId != null}" th:with="s=${sheetById[r.logSheetId]}"` on the same tag is genuinely safe and the pattern to copy. The case that bites is a request with no actor — a pool sheet with no assignee auto-submitting at its deadline raises one — and the page 500s for everybody the moment such a row appears.

68. **Bulk imports produce one async audit task per saved row, and the audit queue is bounded — fixed, but understand the shape before you add another bulk writer.** `RepositoryAuditAspect` advises every `CrudRepository.save`, so importing N rows enqueues N tasks onto `auditExecutor`. A tight import loop is an unbounded producer against a bounded queue; with the old `queueCapacity` 256 and the **default AbortPolicy**, filling it threw `TaskRejectedException` **into the import thread**, whose message — "ExecutorService in active state did not accept task" — names an executor that has nothing to do with importing and mentions no row. Three things fix it, and the third is the one worth remembering: (a) `auditExecutor` now uses **`CallerRunsPolicy`** with `queueCapacity` 2000, so overflow makes the producer do the INSERT itself and the import merely slows down; (b) `ImportJob`/`ImportJobError` are in `AuditEntitySupport.EXCLUDED_TYPES`; (c) **the failure handler was the second casualty.** `fail()` saves the entity, that save enqueued an audit task, the queue was still full, and the rejection escaped *from inside the catch block* — so the job was never marked at all and sat at `RUNNING` forever. Recording that something failed must not depend on anything that can fail; `forceFail()` is a native UPDATE for exactly that. Measured on live data: a 9,942-row import left 1,294 `import_job_errors` and 1,280 `import_jobs` audit rows — 57% of the whole trail was the job's own paperwork. If you add another loop that writes thousands of entities, check what its *bookkeeping* enqueues, not just its payload.

69. **A `fetch()` POST with no CSRF token is not a 403 — it is a silent no-op, and the button just does nothing.** The web chain has CSRF **enabled** (`WebSecurityConfig` disables it only for `/api/**`). Miss the token and `MissingCsrfTokenException` — an `AccessDeniedException` — reaches `WebAccessDeniedHandler`, which answers with **`sendRedirect`**, not a status code. `fetch` follows redirects by default, so the caller gets the dashboard HTML with **status 200**; `res.json()` then throws a `SyntaxError` inside an `async` function whose rejection nobody awaited. Nothing is logged in the browser, nothing is shown to the user, and the click looks like it did nothing — which is precisely how the batch-import Stop and Delete buttons were dead for every click without anyone noticing. Verified live: `{status: 200, redirected: true, url: "http://localhost:8081/", parseError: "Unexpected token '<'"}`. Use **`AppCsrf.postJson()`** (`static/js/csrf.js`) for every state-changing fetch: it sends the header from the `<meta name="_csrf">` tags the layout publishes, sets `redirect: 'manual'` so a rejected POST cannot masquerade as a 200, and throws a readable Persian message. A Thymeleaf `<form th:action method="post">` is *not* affected — Thymeleaf injects the hidden field — which is why the upload form worked while every button beside it did not, and why this is invisible when you test by submitting forms.

70. **Server-rendered `disabled` plus a poller that only redraws part of the page means the page never recovers.** `/batch-import` rendered its submit button from `importBusy` (a model attribute) and polled only `#jobsBody`; when the import finished, the table went live but the form stayed disabled until a full reload — so a *successful* import looked exactly like a running one. Two rules fall out. **Anything the poller must be able to turn off has to exist in the DOM**: `th:if` emits nothing, and JS cannot toggle an element that was never rendered — use `th:classappend="… ? '' : 'd-none'"` and toggle the class. And **do not let the client infer server state it cannot see**: the job list is scoped to the caller while the submit gate (`assertNoActiveImport`) is system-wide, so `jobs.some(j => j.active)` would happily re-enable the form while another user's import was running. `GET /batch-import/jobs` returns `{busy, jobs}` for that reason.

71. **`catch (Exception)` in an async worker is not a safety net — `Error` walks straight through it.** `ImportJobRunner` caught `Exception`, but the realistic death of a large import is `OutOfMemoryError` (the whole workbook is read into heap at once by `new XSSFWorkbook(...)`), which is an `Error`. The thread ended, nothing wrote a status, and the row stayed `RUNNING` — and because `assertNoActiveImport()` is system-wide, **one wedged row blocked every user's next import**, with `ImportJobRecoveryRunner` running only at boot. That is why "restart the application" used to be the documented remedy. Now: `catch (Throwable)` marks the job then rethrows any `Error`; `ImportJobWatchdog` fails jobs whose `heartbeat_at` has not moved for `app.import.stale-timeout-minutes`; and an admin can force-abandon a stalled job from the UI. If you write another cooperative-cancellation worker, give it a heartbeat — a flag the dead thread is supposed to read is not a cancellation mechanism.

72. **MDC set after `chain.doFilter` is dead code, and "the user is in the logs" was an illusion.** `RequestMdcFilter` resolved the username *after* the chain returned and then cleared the MDC in the same `finally` — written after every log line for the request, erased before anything read it. The username still appeared on most lines only because `LoggingAspect` sets it again per advised method, which left it missing exactly where it matters: `web/advice/**` (explicitly excluded from the pointcut — the global exception handlers), `WebAccessDeniedHandler`, `JwtAuthenticationFilter`, and anything logged by Spring or Hibernate. The fix is `UserMdcFilter`, and **where it is registered is the whole point**: as an ordinary servlet filter ordered after Spring Security it still reported `anonymous` for a CSRF denial, because that denial is raised by `CsrfFilter` and handled by `ExceptionTranslationFilter` *inside* the chain, which a downstream filter never enters. It is registered with `addFilterAfter(…, SecurityContextHolderFilter.class)` on the web chain and after the JWT filter on the API chain. It is deliberately not a `@Component` — Boot would auto-register a second copy, and `OncePerRequestFilter` keys its guard on the class name, so the outer copy would mark the request filtered and the one inside the chain would skip.

73. **One log file per question, or the useful one drowns.** Audit rows were written to `business.log` at one line per changed *field*: 42,498 lines against ~40 real business events on live data, 9.8 MB against 708 KB of `app.log`. Nobody could answer "what did the system do" from a file that was 99.8% something else. Volume is the signal to split — `audit.log` now has its own logger (`…audittrail`, a synthetic name so it does not also capture the real `audit` package), its own appender, its own retention, and **one summary line per change** with field *names* only. Values stay in the `audit_log` table, which is the authoritative copy and has an admin page; duplicating them into a plain file with different retention is a second home for data that already has one.

74. **A rule written against a role's CODE is not inherited by a copy of that role — this is fixed, keep it fixed.** "ساخت نقش مشابه" copies `role_permissions` and assigns a **new code**. Every check of the form `isAdmin()` / `hasRole("HIGH_USER")` / `isUnitScopedOnly() = !ADMIN && !HIGH_USER` therefore stopped recognising the copy: a duplicate of ADMIN held all 123 permissions and still could not view another user's import job, complete an unassigned sheet, or see outside its own units — while the server would have accepted every one of those calls through `@PreAuthorize`. It failed *safe* (a copy was always more restricted) which is exactly why nobody noticed; it surfaced only as "this role has the permission and still gets access denied". Those decisions are now **capabilities** — `CAP:*` rows in `permissions` with `category='capability'` and null method/path — read via `SecurityUtils.hasCapability`. They live in `permissions` rather than a new table precisely because role duplication already copies that, so copyability is solved by construction and the mobile login response carries them with no API change (which is how the PWA dropped its own role checks). Four things keep it working: (a) capabilities are phrased **positively**, so absence means restricted and a custom role with every endpoint ticked is still unit-scoped; (b) `RoleService` refuses to strip a **system** role's capabilities, because moving ADMIN's power into data made it removable from the Roles page for the first time; (c) `SystemRoleCapabilities` duplicates the grant matrix for the two callers that cannot read the database — the guard in (b) and the test fixtures — and `CapabilitySeedIntegrationTest` fails on drift; (d) `NoRoleCodeAuthorizationTest` scans the source and fails the build if `isAdmin(`/`hasRole(`/a hard-coded role name returns outside three allow-listed files (`SystemRoleCapabilities`, `AdminBootstrapRunner` — provisioning, and `ExcelImportService` — which parses `StaffRole` from the unit-staff sheet, same words, different concept). Unit **scope** is a separate axis and deliberately still keys off real `unit_supervisors` rows.

75. **A new Excel column goes where it cannot be misread, and for `users` that meant appending — the opposite of gotcha #35, on purpose.** `users.org_unit` / `org_position` (V4) were added at the **end** of the import layout (indices 11, 12) rather than beside `shift` where they belong logically. `ExcelImportService` reads by position and never validates the header row, so the only question that matters is what happens to a file an administrator downloaded *before* the change: appended columns leave indices 0–10 untouched, the two new cells read blank, and both fields are optional — the old file imports exactly as it did. Inserting them mid-layout would have shifted `password` onward, read `roleCodes` as `active`, and reported success. #35 chose insertion for `nameFa` precisely because there the shift makes the next lookup fail *loudly* ("Parent location not found"), which beats silence — the shared rule is **never allow a silent misread**, not "always insert" or "always append". Three files carry this layout independently and drift silently: the parser in `ExcelImportService.importUsers`, the header in `UserWebController#downloadTemplate`, and the prose in `users.html`; `isBlankRow(row, N)` has to grow with them, or a row carrying only the new columns is treated as empty and dropped. `UserOrganizationFieldsIntegrationTest` fills the *downloaded template itself* and asserts each value lands in the field its header names, which is what catches any of the three moving alone. Separately: `org_unit` is free text on the person and has **nothing** to do with `operational_units` (the access-scoping structure) — no FK, no uniqueness, nothing branches on it. Keep it that way; a foreign key there would let an HR typo change somebody's access scope.

76. **Folding an already-applied migration back into an earlier one needs a manual Flyway repair, and `target/classes` is the step everyone forgets.** `users.org_unit`/`org_position` and the two `app_settings` policy seeds shipped briefly as V4 and V5, then moved into V3 because **production is still on V2** — it has never seen V3, so it gets the whole thing as one migration instead of three. Development databases had already applied V3 and V4, so the files could not simply be edited: Flyway compares a checksum. The repair that works, in order: (1) `pg_dump` first — this is history-table surgery; (2) merge the SQL into V3 and delete the V4/V5 files; (3) recompute V3's checksum and `UPDATE flyway_schema_history SET checksum = … WHERE version = '3'`, then `DELETE … WHERE version = '4'` (its DDL is already applied to that database, so only the bookkeeping moves); (4) run V5's `INSERT … ON CONFLICT DO NOTHING` by hand, since no migration will replay it; (5) **delete the stale copies from `target/classes/db/migration/`** — `spring-boot:run` reads migrations from there, not from `src`, and a `mvn` build copies resources without removing deleted ones, so the app cheerfully re-ran the V4 file that no longer existed and failed with `column "org_unit" of relation "users" already exists`. Flyway's checksum is a CRC32 over each line's UTF-8 bytes with line terminators excluded and the BOM stripped from the first line; **verify any reimplementation against the checksums already in `flyway_schema_history`** before writing one back — all three matched here before the new value was computed. Proof it worked: `Successfully validated 3 migrations` + `Schema "public" is up to date` on a real boot, and the Testcontainers suite, which builds every database from V1 → V3 and therefore also exercises production's V2 → V3 path. **It happened a second time** — `nfc.manual_entry_enabled` shipped as V4 and was folded into V3 for the same reason — and step (5) caught the same person out again: the source file was deleted, `find` reported nothing (from the wrong working directory), and the very next boot re-applied V4 from `target/classes` and re-inserted its history row. The tell is a history table that grows a row back after you deleted it. **Check `target/classes/db/migration/` explicitly, from the project root, before restarting** — and re-run the repair afterwards, because the stray boot rewrote both the checksum and the row.

77. **A `@Component` filter that can write a response is registered TWICE, and the second copy runs on every URL in the application.** Boot auto-registers every `Filter` bean against `/*`, on top of wherever `WebSecurityConfig` places it. That is harmless for `JwtAuthenticationFilter`, which only ever tries to authenticate and then calls `doFilter` — a second pass changes nothing. `IntegrationApiKeyFilter` **terminates** the request with a 401 when there is no `X-API-Key` header, so the auto-registered copy answered that 401 to *everything*: the login page, `/api/health`, every CSS and font request. The whole panel was unreachable, and the response was an English integration-API error on a Persian admin login screen. **All 1,356 tests passed against it.** `MockMvcBuilders.webAppContextSetup(...).apply(springSecurity())` builds the Spring Security chain and nothing else, so Boot's auto-registered copy does not exist in a MockMvc test — the entire suite is blind to this class of fault by construction. One live `curl http://localhost:8081/login` found it in a second. Two fixes, and a new filter needs one of them: a `FilterRegistrationBean` with `setEnabled(false)` (what `WebSecurityConfig.integrationApiKeyFilterRegistration` does — keeps constructor injection, which matters for a filter with dependencies), or not being a `@Component` at all (what `UserMdcFilter` does — see #72, which is the *same* auto-registration trap arriving from the opposite direction, where the duplicate silently swallowed the request instead of failing it). Guarded by `IntegrationFilterScopeIntegrationTest`, which starts a **real servlet container** because that is the only arrangement where the fault is visible; it was verified to fail four ways when the registration is re-enabled.

79. **An exact-name secret list leaks the moment somebody names a field naturally — the login JWT was in `app.log` in clear text.** `LogSanitizer` matched a closed list of field names, and its regex anchors on the opening quote, so `"token"` was masked and **`"accessToken"` was not** — which is what `LoginResponse` and `JwtService.JwtToken` both call the field. `LoggingAspect` serialised the whole `ResponseEntity` body at INFO on every `/api/**` call, so every mobile login wrote a replayable credential to disk, valid until the token expired or somebody revoked the session by hand. **Two things hid it.** First, the aspect's own truncation: an admin holds ~123 permissions, `permissions` is serialised *before* `accessToken`, and the line blew past `MAX_JSON_LENGTH` (4,000) before reaching the token — so testing as `admin` shows nothing wrong, while an operator with eleven permissions leaks in full. 80. **A Logback appender attached to the root logger captures none of this application's own output.** `logback-spring.xml` declares `com.hnp.backendofflinefirst` — and `…business` and `…audittrail` under it — with `additivity="false"`, because each writes to its own file. 81. **Overriding one Actuator health group changes how the other one resolves.** Readiness did not include the database — Boot's default group is `readinessState` alone, so `/actuator/health/readiness` stayed green with PostgreSQL unreachable and a load balancer would have kept routing traffic that could only fail. 82. **A principal identified by username stops being the same principal when the account is renamed — and three separate things quietly broke on that.** `AppUserDetails.equals` compared usernames, which Spring Security's `SessionRegistry` uses as the map key for `maximumSessions(1)`. So: (a) the one-session-per-user limit was **bypassable** — rename, log in again, and the registry saw a different principal and kept both browsers; (b) an administrator deactivating a renamed user searched the registry under the *new* name while the registry held the *old* one, matched nothing, and left the old browser fully live — the call site even carried a comment claiming it handled exactly this; (c) freeing a username and giving it to somebody else made two different people compare equal. Guarded by `AppUserDetailsIdentityTest` (including the equals/hashCode contract over every pair) and four rename cases in `UserDeactivationRevokesSessionsIntegrationTest`.

83. **`api_sessions.user_id` is `ON DELETE CASCADE`, so a deleted user's sessions vanish rather than being revoked.** Worth knowing before writing an assertion about them: the explicit `USER_DELETED` revoke in `UserService.delete` is stamped and then immediately cascaded away, so no row ever carries that reason in practice. 84. **An async write plus *any* foreign key loses rows, and the loss is invisible — `ON DELETE SET NULL` does not fix it.** `audit_log.actor_user_id` was `ON DELETE RESTRICT` while audit rows are written on `auditExecutor`. So: a user acts, the INSERT is queued, an administrator deletes them, `UserService.hasAppActivity` asks whether any audit row names them — and sees only rows already **written**, never the one still in the queue — the delete is permitted, and the queued INSERT then dies on the foreign key. `AuditWriteService` catches it and warns, so nothing fails: one full `mvn test` run logged **42** `Audit row lost … violates foreign key constraint "fk_audit_log_actor_user"` warnings with all 1472 tests green. That is exactly how it behaves in production.<br><br>**The first fix was wrong and stayed wrong for a release.** `ON DELETE SET NULL` looks like the answer and is not: a referential action fires when the *parent* row is deleted and rewrites the children that exist **at that moment**. These rows do not exist yet — they arrive afterwards carrying an id that no longer resolves, so there is nothing for SET NULL to act on and the late INSERT violates the constraint exactly as under RESTRICT. It repairs only the case where the row was already written, which is the one case `hasAppActivity` already refuses. Generalise it: **a referential action cannot protect a write that has not happened yet.** If a table is written asynchronously, ask what its foreign keys do to a write that lands late — the answer is always "reject it".<br><br>V3 section 5 therefore **drops the constraint**. `actor_user_id` is not a live reference but a fact about the past, which stays true after the account is gone — the same reason `actor_username` is denormalised beside it. Nothing dereferences the id (plain `Long`, no `@ManyToOne`, no join, UI shows the username) and `ddl-auto=validate` ignores foreign keys. The delete guard is unaffected: it is `existsByActorUserId`, a query, which never needed a constraint. Draining the queue before each delete was rejected — it leaves the trail depending on winning a race and couples deleting a user to the health of the audit executor. `log_sheet_action_log` keeps its three RESTRICT keys because `LogSheetActionLogger` writes **synchronously**, so its rows are always visible to the guard first — an earlier comment in V3 claimed it "has no FK at all", which was simply false. `AuditTrailOutlivesUserIntegrationTest` covers all of it, including a direct `pg_constraint` assertion so re-adding the key fails with an explanation rather than losing rows quietly.

85. **`try/catch` inside an `@Async @Transactional` method does not catch the failure you care about.** The constraint violation marks the transaction rollback-only, and the *commit* — which happens after the method returns — throws `UnexpectedRollbackException` outside the try block, on the async thread, where it reaches only `SimpleAsyncUncaughtExceptionHandler` and is reported as "Transaction silently rolled back" naming neither the row nor the cause. Observed while fixing #84: the catch was there, the WARN never appeared. The transaction has to live in a **separate bean** so the commit happens inside the caller's try — `AuditWriteService` → `AuditRowWriter`, and `ApiKeyUsageWriteService` → `ApiKeyUsageRowWriter`, both of which had the same shape. Same separate-bean reason as `AuditLogPurgeService`, arrived at from the opposite direction.

86. **Collapsing several unreleased migrations into one needs a hand repair of `flyway_schema_history`, and Flyway cannot do it for you.** V3, V4 and V5 were all developed after the last release, so they were merged into a single V3 — production is still on V2 and should advance by one version, not four, for changes it has never seen. Development and test databases had all three applied, and there is no Flyway command for "these three rows are now this one": `repair` realigns checksums for migrations that still exist, and `validate` simply refuses to boot. The procedure, in order: (1) delete the file(s) being merged away and **also delete their stale copies from `target/classes/db/migration/`** — Flyway resolves from the classpath, so a leftover there produces `Found more than one migration with version 3` and the boot fails before it reaches anything useful; (2) `DELETE FROM flyway_schema_history WHERE version IN ('4','5')`; (3) `UPDATE` the surviving row's `script` and `description` to match the new file — Flyway validates both, not only the checksum; (4) set `checksum = 0`, boot once, and read the real value out of the error (`Resolved locally: -2108127115`); (5) `UPDATE` the checksum to that and boot again.<br><br>The checksum can also be computed directly, which avoids the two extra boots: Flyway CRC32s **each line's UTF-8 bytes with no line terminator**, i.e. `for line in text.splitlines(): crc = crc32(line.encode('utf-8'), crc)`, as a signed 32-bit int. Only trust it after validating the method on this repository: computing V1 and V2 must reproduce `156897951` and `1738864484` exactly, which are the values already in `flyway_schema_history`. If they do not match, fall back to reading the value out of the boot error.

87. **"Is this entry empty?" and "does this device have an opinion about it?" are different questions, and answering the second with the first has now cost data twice — in opposite directions.** The PWA merge asked `Object.keys(localForm).length > 0` (key presence): the web fill form writes every field of every entry on every save, so an asset nobody touched arrived as `{"Bar": "", "Status": ""}` and counted as work — the device then won every asset in that sheet forever, a supervisor's readings went invisible, and the next submit blanked them (log sheet 85). Changing it to `hasEntryFormData` (value presence) fixed that and broke the mirror image: a *deliberate clear* reads as no opinion, so the next periodic sync restored the value the operator had just removed, before they could submit. Neither predicate is wrong; both are the wrong question. Value presence then failed a third time, in the direction that matters most: it **cannot tell a value the device entered from one it was sent**. After any sync the device holds this server's own readings, so value presence is true for every filled entry on every synced tablet — and a supervisor correcting a reading in the browser reached a device that had already decided it owned the entry, so the correction never appeared and the tablet's next submit wrote the stale value back over it. The opinion is therefore recorded when it is formed — `locallyEditedAt`, stamped by `applyOperatorEntrySave` on every save including an emptying one, and set by nothing that receives from the server — and it is now the **only** thing the merge reads. Rows from builds older than the marker are stamped **once**, by the PWA's `version(2)` migration, rather than by a permanent OR arm that would run on every merge forever and carry the failure with it. **Do not express this by bumping `updatedAt` on a clearing save**: `createdAt`/`updatedAt` are the base the device echoes to the server, and `wouldBlankUnseenAnswer` compares them for equality, so moving them would make the server refuse every deliberate clear. Related, and worth knowing before "unifying" anything: the device deliberately keeps **three** emptiness rules — `entryTimestamps.isValueFilled` (sync), `entryCompletion.isValueFilled` (UI progress) and `formDataValidation.isFieldValueBlank` (mirrors the server's `isBlank`), the last with a written explanation of why it does not reuse the second.

88. **The web fill form and a mobile submit both send the WHOLE sheet, not the part that changed.** `applyWebEntryValues` iterates every entry the form posted and `mergeMobileEntryUpdates` every entry the device sent — and each device resends every asset it holds, including ones the operator never opened. Any rule written as "what arrived is what the actor meant" is therefore wrong on both paths. Two consequences are now handled explicitly: `storableFormData` drops unanswered keys so a save cannot write blanks onto assets nobody touched (#87), and `wouldBlankUnseenAnswer` refuses a payload that would erase a stored answer the device never saw. That guard compares the entry's `(created_at, updated_at)` pair for **equality**, not ordering: the device echoes back whatever the last bundle gave it for an entry it did not touch, so a match means "up to date" and no two clocks are ever compared. A match therefore still lets a clear through — clearing a reading you can see is a real thing operators do.

89. **The asset-count ceiling is enforced in one place and only warned about in another, and that asymmetry is the design.** `LogSheetSizeLimits` refuses above `max` when a **person is at the screen** — saving a template, creating a custom sheet — and the scheduler only warns and generates anyway. Refusing in the scheduler looks safer and is worse: a `SCOPE` template re-resolves its hierarchy on every run, so one that was well inside the limit when it was saved crosses it the day somebody registers a new plant system, with nobody having edited anything. The round would then silently not happen, and the shift would find no work with nothing to look at but an absence. A big sheet is a visible failure; a missing round is not. `max <= 0` disables the refusal entirely and the warning still fires, because "you asked for this" and "nobody should ever hear about it" are different statements.

90. **A local-only "I have an opinion" marker is only safe if something reliably forgets it.** `locallyEditedAt` makes the device win an entry against the server. Left standing after the work is delivered, it makes the device win that entry *forever* — the supervisor edits the reopened sheet and the operator never sees it, which is gotcha #87's first failure back again. Two independent mechanisms, deliberately not one: the marker is cleared when the server accepts the submission (`SUBMITTED`/`DUPLICATE`) and whenever a row is reset (`clearLocalEditMarkers`), **and** `applyLogSheetBundle` ignores markers entirely on a row that is already `submitted` + `synced`. The second exists because the first has a hole that is easy to reintroduce: the reopen-and-continue path calls `resetLogSheetToOpenDraft` **without** `clearEntryFormData` — correctly, the operator is carrying on with their own readings — and that turns a delivered row back into a draft, re-arming the gate. `localEditMarker.test.ts` exercises each mechanism on its own so neither can quietly stop working behind the other.

91. **Working "by accident" is a reason to change it, not a reason to leave it — especially when what it guards fails silently.** `logback-spring.xml` nested `<springProfile>` inside each of its five encoder-owning appenders to pick that appender's encoder. Spring Boot documents and implements the element as **top-level only**, and said so at every boot: eleven `SpringProfileIfNestedWithinSecondPhaseElementSanityChecker` warnings. The selection worked regardless, so it was left alone and the warnings were written up as expected noise. That reasoning was backwards. The construction is rejected by the framework, and the failure it protects against is invisible: if a release stops honouring the nesting, the application still logs perfectly happily — in text, into a Logstash pipeline that indexes none of it — and nobody finds out until they need the logs. **A silent failure mode may not rest on unsupported behaviour.**<br><br>The fix is the supported shape: two top-level `<springProfile>` blocks, each declaring the five appenders. The objection to that had been duplication — a rotation policy or size cap drifting between the two formats loses production logs in whichever one nobody reads. So **no value lives inside a branch**: paths, archive patterns, histories and caps are properties at the top of the file that both branches reference, and `LogbackProfileConfigTest.theTwoBranchesAgreeOnEverythingButTheEncoder` canonicalises each appender with its `<encoder>` stripped and compares the branches, so any other difference fails the build. What is duplicated is XML structure, not configuration. The AsyncAppenders, loggers and `<root>` own no encoder and stay declared once, after both branches, resolving their `appender-ref`s against whichever branch survived.<br><br>Two things found while doing it, both worth the habit they suggest. The file's header credited `JsonLogProfileIntegrationTest` and `PlainTextLogProfileIntegrationTest` with asserting the runtime encoder resolution; **neither has ever existed in this repository** — `LogbackProfileConfigTest` records that runtime tests were tried and removed for being order-dependent (logback's config is JVM-global and Spring caches contexts, so whichever profile initialises logging last wins). And the same header said "each of the nine appenders below nests two of them", when only five ever did. A comment that names a test is a claim; check that the test exists.

92. **A JWT claim is a statement by whoever holds the signing key, not by the server — so authorities must never come from one.** `JwtService` wrote `roles` and `perms` into every token and `JwtAuthenticationFilter` turned them straight into the request's authorities. The signing key ships in `application.properties` as a working default, so on any deployment that did not replace it, "who can read this repository" and "who can grant themselves every permission in the system" were the same set. The session registry did not help: it asked only whether the `jti` named a live row, so an ordinary operator could log in, take their own genuine `jti`, and re-sign the payload with `perms` listing anything. Demonstrated, not reasoned about — with the old code restored, `JwtForgeryIntegrationTest.aForgedRolesClaimGrantsNothing` gets **400** from a privileged endpoint instead of 403, meaning the forged claim carried it past `@PreAuthorize`.<br><br>**The two halves are both required, and each is useless alone.** Reading authorities from the database stops privilege forgery but not impersonation — a forger pairs their own `jti` with somebody else's `uid` and gets *that user's* real permissions. Binding the `jti` to the `uid` stops impersonation but not forgery — they keep their own `uid` and simply claim more perms. Both, and a leaked key grants nothing: `ApiTokenAuthenticator` verifies the signature, checks the `jti` is a live session **of that user**, loads the user and refuses them if deleted or deactivated, and takes the authorities from `AppUserDetailsService.loadById`.<br><br>Three consequences worth knowing. **A permission change is now in force on the next request**, not at token expiry — which turned `FaMessages.rolesChangedSessionsStillOpen` into a lie and it had to be rewritten as `rolesChangedWebSessionStillOpen`, since only the *browser* still holds access captured at login. **Resolution is by `uid`, never by `sub`**, so a renamed user's token keeps working (same reasoning as #82). And **the registry caps a forged `exp`**: the per-request check reads `api_sessions.expires_at`, so a token claiming ten years dies with its row.<br><br>The cost is three indexed reads per API request, uncached on purpose: the PWA syncs every 30 seconds, so fifty tablets is under two requests a second — and a cache would put "I have removed their access" back into the future by exactly the cache's lifetime, which is the property the change exists to provide.

93. **A `<form>` inside a `<form>` is not nested — the inner one is DELETED by the parser, and the button inside it now submits the outer form.** Every master-data list page wrapped its table in the bulk-delete form, and each row carried its own little delete form. HTML forbids the nesting: the parser ignores the inner `<form>` start tag, so the **first row's** trash button became a submit button of `bulkDeleteForm` and posted to `/x/delete-bulk` instead of `/x/{id}/delete`. With nothing ticked `bulk-delete.js` cancelled the submit and the button did nothing at all; with other rows ticked it would have deleted *those*. Rows 2+ were unaffected, which is why it survived — the bug is invisible unless you click the top row.<br><br>Found by reading `button.form.action` in a real browser, not from the template, where the markup looks perfectly correct. **The template source cannot tell you what the DOM is**; for anything involving form association, ask the browser. The fix is the `form="…"` attribute: the bulk form is now a standalone element before the table and each checkbox joins it by id, so nothing nests. `bulk-delete.js` consequently scopes its queries to the `[data-bulk-delete]` container — a control associated by attribute is **not** a descendant, so `form.querySelectorAll` finds none of them. Affects all six pages: locations, plant systems, main/sub functions, asset entries, operational units.

94. **An HTML `pattern` attribute that fails to compile is silently IGNORED, and the `v` flag makes that easy to trigger.** The field-key input shipped `pattern="[A-Za-z0-9_-]+"` — valid in Java, valid in `grep`, valid under the regex `u` flag, and read by every reviewer as obviously correct. Browsers compile a `pattern` as `^(?:…)$` **with the `v` flag**, where an unescaped `-` at the end of a character class is `Invalid character in character class`. The spec says an uncompilable pattern is ignored, so the field accepted everything: `Bearing Housing`, `V.1`, `دما` and `=temp` all passed `checkValidity()`. Write it `[A-Za-z0-9_\-]+`, which compiles under both flags.<br><br>The server-side rule never had the problem (Java has no `v` flag), so the only symptom was a validation message appearing after a round trip instead of in the form — which reads like a design choice rather than a defect. `FormPatternAttributeTest` now scans every template for the construct and fails the build on it. Generalise: **a declarative validation that fails open is worse than none**, because it is indistinguishable from one that is working, and the two `pattern` attributes here had been wrong since they were written.

95. **The layout already renders every flash message — a page that renders one again shows it twice.** `fragments/layout.html` emits `${successMessage}`, `${errorMessage}`, `${warningMessage}` and `${importErrors}` into `.app-main` before it drops in the page content, so a controller only has to set the attribute. `asset-status-requests.html` also rendered `successMessage` and `errorMessage` inside its own content, and the result was the same sentence twice on that page — invisible while the flash was an inline strip, obvious the moment they became toasts (two cards, same text). 96. **A script cannot remove a flash of the wrong styling — only markup can.** The toast stack was first built in JavaScript: the server rendered a plain Bootstrap `.alert` inside `<main>` and `enterprise-ui.js` moved it into a fixed stack and rebuilt it on `DOMContentLoaded`. 100. **A history row must be gated on the same flag that decides re-attribution, or the two will disagree.** `log_sheet_entry_revisions` keeps the reading a correction replaced. 101. **`ddl-auto=validate` proves the entity matches the schema; only a live run proves the page renders.** Both new panels on the log-sheet detail page compiled, passed the whole suite, and were wrong in ways no test could see — the «آخرین ذخیره پیش‌نویس» block **duplicated** an item the page had already rendered for years a few rows further down, and the `START` action row the design called for was never written at all (the column was set, the log row was not), which only showed up as an empty `log_sheet_action_log` on a real sheet. Neither is a failing assertion anywhere; both are obvious in ten seconds on the running app. The rule in CLAUDE.md is not a formality.

102. **`form_data` holds only answered fields, so anything that renders from its keys can only ever show what was filled.** The log-sheet detail page listed a row per key. An asset whose class defines seven parameters and whose operator recorded three rendered three rows, and the four they skipped were **indistinguishable from parameters the class does not define** — which is the single question a supervisor opens that page to answer. An asset nobody touched rendered a bare «—», saying nothing about what the round had asked for.<br><br>The data is right and must stay as it is: a key present only when there is a real answer is what makes `max_severity IS NOT NULL` an exact has-a-reading test, and what stops one supervisor save writing `{"Bar": "", "Status": ""}` onto forty entries (gotchas #87–#88). **It is the display that has to ask the other question** — `FormDataViewHelper.allRows` enumerates the sheet's frozen schema instead, so every parameter appears in its `order` and an unanswered one renders «ثبت نشده». Keys the schema no longer defines are appended rather than dropped, or a sheet frozen before a field was retired would quietly lose a measurement (roadmap.md §5).<br><br>Three things are deliberate. `rows` is **unchanged**, because the voided-submission page shows what one refused payload literally carried and padding it would misrepresent it. An unanswered number is **not** evaluated against its bands — asking would paint every empty row red on any class whose minimum is above zero. And the «فقط دارای مقدار» toggle is **client-side over already-rendered rows** (`data-param-state`), because the entry search and the entry filter re-run over those same rows constantly and anything re-rendering here would fight them.<br><br>Generalise: **when a storage rule is right and the display is wrong, change the question the display asks — not the data.** Regression: `LogSheetDetailParametersIntegrationTest` asserts against the rendered HTML, because a unit test on the helper alone passed throughout — the helper was doing exactly what it was asked.
103. **Adding a value to an existing enum silently changes the meaning of every condition that names the old one.** `APPROVED` (V6) is a supervisor's sign-off laid on top of `SUBMITTED`. About **forty** conditions across services, reports and templates asked "was this round completed?" by writing `status == SUBMITTED`, and every one of them was correct until the day a second completed status existed. There is no error and no failing test for a missed one — just a smaller number in a report about a plant, and a page quietly missing a row.<br><br>Do not rely on grepping carefully once. `LogSheetStatus.COMPLETED_STATUSES` / `isCompleted()` is the only way to ask; `LogSheetViewHelper.isCompleted / isAwaitingApproval / isApproved` are the only way a *template* asks, so no template names a status itself; and **`CompletedStatusConditionTest` fails the build** for anything naming `SUBMITTED` alone outside a four-file allow-list of genuine transition guards. The guard is what makes this safe to do again — it listed all forty sites on its first run, which is also how they were found.<br><br>Two traps inside the change. `isAwaitingApproval` means *exactly* `SUBMITTED` and is the precondition for approve **and** void **and** reopen alike, so the buttons and the service can never disagree — offering an action the service will refuse is worse than not offering it. And `COMPLETABLE_STATUSES` deliberately **excludes** `APPROVED`, so a tablet offline since before the approval has its payload preserved as a void submission rather than silently overwriting reviewed work. On the PWA the same status has a sharper failure: `alignLocalWorkflowWithServer` ends every branch in `return null` meaning "nothing to do", so an *unhandled* status leaves a stale local draft alive and editable for a round the server has closed — the operator submits it, the server voids it as superseded, and from their side the work vanished. Hence `isCompletedServerStatus` in `src/types`.
104. **Thymeleaf copies `<!-- … -->` into the response verbatim, so an explanatory comment inside a `th:each` is emitted once per row.** Measured on a real 23-asset log-sheet page: **301 KB of a 639 KB response was HTML comments**, 247 KB of it a single paragraph repeated 329 times. Nothing is slow on the server; it is bandwidth and parse time on a tablet over plant wifi, and it is invisible in review because the template looks fine.<br><br>The fix is not to delete the explanations — write them as **parser-level** comments, `<!--/* … */-->`, which Thymeleaf strips when it parses the template. Same text, same place, never sent. Only comments inside a loop matter; a page preamble emitted once is worth leaving readable in view-source. Regression: `LogSheetDetailParametersIntegrationTest.noCommentIsCopiedIntoTheResponseOncePerRow` fails if any comment appears more than three times in one rendered page, and names the offender.
105. **A pager that enumerates filter names drops every filter it has not been told about.** `fragments/list-toolbar :: pagination` built its links from four hard-coded parameters — `q`, `status`, `asset`, `classId` — read out of the model. Any page whose filter was called something else lost it on «بعدی»: `/asset-status-requests` filters by `status` and `assetId`, `/reports/asset-parameters` by `assetId`, `fieldKey`, `from` and `to`. The user saw a filtered first page, clicked through, and silently got page two of the **unfiltered** list. The only symptom is that the rows stop matching, which reads as a data problem rather than a navigation one.<br><br>`ListFilterAdvice` stops enumerating: it puts the request's *own* query string, minus `page` and `size`, into the model as `filterQuery`, and the fragment appends it. A page that adds a filter tomorrow keeps it across paging with no change to the fragment. Two details that bite: `page` and `size` **must** be excluded because the pager supplies them, and Spring binds the *first* occurrence of a duplicated parameter — so leaving `page` in would make every link navigate to the page you are already on. And `@ControllerAdvice`'s selectors are **OR-ed, not AND-ed** (`HandlerTypePredicate.test` returns on the first match), so adding `annotations = Controller.class` to narrow `basePackages` would have *widened* it to every controller in the application.
106. **A deleted attachment leaves an id that resolves to nothing, and "missing" cannot say why.** `log_sheet_entry_revisions.form_data` keeps the reading a correction replaced, and when that reading was a photo or a voice note the row holds attachment **ids** — while `AttachmentService.delete` removes the row and the bytes outright. The history panel could only render «فایل پیوست در دسترس نیست», which reads identically to storage having lost the file and says nothing about what the removed evidence was. `attachment_snapshot` (V6) captures kind, mime type, size, duration and who captured it when, **at revision time**, because by the time anybody reads the history the rows it describes may be gone.<br><br>Three decisions worth keeping. The **live row wins** where it still exists — a correction that merely detached a photo from a field left bytes that can still be opened, and a thumbnail beats a description of one. A snapshot-only attachment renders as a struck-through «حذف‌شده» chip and is deliberately **not a link and not an `<img>`**: a thumbnail pointing at a 404 is worse than saying what was removed, and it must stay distinguishable from `missing`, which means nothing knows what the id ever was. And the **bytes are still gone** — keeping those is a soft-delete design with a disk-retention story behind it, deliberately not taken on.
107. **SpEL throws on a null map index rather than yielding null — so one nullable id is a 500 on the whole page, not a blank cell.** `nfc-fault-reports.html` wrote `userById[r.reviewedByUserId]` inside the reviewed branch. `reviewed_by_user_id` is nullable, and a single such row took out the entire queue for everybody, with a message naming a template line rather than the data. The null check on the **id** has to come first: `${r.reviewedByUserId != null and userById[r.reviewedByUserId] != null}`. This is the same trap already listed for map indexing elsewhere in this file, found again in a new template — which is the argument for grepping every `[...]` index whose key is a nullable column whenever you touch a page. Found by an integration test whose fixture happened to be honest about the schema; it is not reachable through the UI, because the service always sets the reviewer.
108. **A per-field ceiling that counts rows rather than references is a dead end waiting to happen.** `AttachmentService.enforceCount` counted every `attachments` row for a (sheet, asset, field, kind). An operator on a **one-video** field recorded a clip, it uploaded, they re-recorded — and the device's server-side delete of the first one never landed. The server then held one video that **nothing referenced**: not the entry's `form_data`, not a revision, not a void submission. The field was full forever and the replacement was refused on every sync pass for the rest of the round — `409`, deliberately retryable, retried eleven times in the log and unable to ever succeed. **There was no way out from the tablet**, because an operator cannot delete a file their device has forgotten.<br><br>The ceiling exists to bound evidence, and the evidence is what the reading points at. So an unreferenced row is now a **leftover**, and when the ceiling is otherwise reached the oldest leftover is deleted to make room — the total for a field still never exceeds the configured maximum, so a hand-rolled client can replace but not accumulate. Never reclaimed: anything a revision references (the «مقادیر پیشین» panel) or a void submission references (a refused payload kept for a supervisor to read).<br><br>Two details that decide the arithmetic. **Rows are bounded, not referenced ids**: a reference with no row is either a capture still queued or a pointer left by a delete, indistinguishable, and counting it would turn the second into a *new* dead end where a supervisor deleting a photo in the panel wedges the field. And the path is self-healing rather than exact — an unreferenced row admitted while a referenced one was in flight is a leftover by the time the referenced one lands, so it is the row that gives way. Regression: `AttachmentApiIntegrationTest` §«A capture that replaced one the server still holds».
109. **"Do we know the server has it" and "might the server have it" are different questions, and a delete must ask the second.** The PWA's `removeAttachment` queued a server-side deletion only when `syncStatus === 'synced'`. An upload whose *response* never arrived — a timeout, a 502, a link that dropped after the server committed — leaves the row `pending` or `failed` on the device while the file sits on the server, so the local-only branch orphaned the server's copy and consumed a slot nothing could free (gotcha #108's other half). It now queues one for any row carrying a `logSheetServerId`; a row without one was never uploadable, so there is genuinely nothing to ask about.<br><br>That only works because **DELETE is idempotent**, and it was not: `AttachmentService.delete` threw for an unknown id, which the handler turned into `400`. The tablet's delete queue treats `404` as "already gone, done" and everything else as "leave it queued and stop the pass" — so one row the server had never heard of would have wedged the entire queue, and every deletion behind it, on every future pass. Deleting something that is not there **is** the requested end state; it returns `204` now.

## Photo & audio fields (built)

Class fields can hold photos and voice notes captured on the tablet. This section records the
decisions behind the shipped implementation — read it before touching anything under
`AttachmentService`, `AttachmentStorageService`, or the PWA's `attachmentSync`.

### The decision that shapes everything else: no base64 in `form_data`

Base64 inflates by 33% and — much worse — puts the bytes inside the `jsonb` column. Every read
of the log sheet, every bundle sync, every backup and every report would then carry megabytes
of binary. At the project's own target load a daily sheet is tens of GB a year: fine on a
filesystem, not fine inside `log_sheet_entries.form_data`.

So **the JSON holds references and the bytes live on disk**:

```json
{ "pump_photo": { "type": "attachment", "ids": ["a7f3…", "b2c1…"] } }
```

`AttachmentReferences` parses this on the server and `attachmentIdsOf` on the client. Both are
**tolerant on shape** (a bare array or a single string id is accepted, for data written by an
older client) and **strict on content** (blank and `"null"` entries are dropped — they would be
references that can never resolve). `AttachmentReferences.extract` additionally requires
reference *shape* before reporting a field as holding ids, so `{"pressure": 42}` is never
mistaken for an attachment field.

### Server side

| Piece | Where |
|-------|-------|
| Table | `attachments` in `V1__initial_schema.sql` — `id` VARCHAR(36) **minted by the client**, `log_sheet_id` (CASCADE), `asset_id` (RESTRICT), `field_key`, `kind` (IMAGE/AUDIO/VIDEO), `mime_type`, `size_bytes`, `sha256`, `width`/`height`/`duration_ms`, `storage_key` UNIQUE, `uploaded_at`, `created_by_user_id` |
| Bytes | Filesystem under `app.attachments.storage-dir` (default `./data/attachments`), date-sharded `2026/08/07/<uuid>.<ext>`. **Not** a DB blob — blobs wreck backup and replication. `storage_key` is the indirection that lets S3/MinIO replace the filesystem later without a schema change. |
| Size cap | `app.attachments.max-file-size-bytes` (default 10 MB) |
| Endpoints | `POST /api/attachments` (multipart), `GET /api/attachments/{id}`, `DELETE /api/attachments/{id}` — each with its own permission, granted to SUPERVISOR / OPERATOR / SENIOR_OPERATOR |
| Field types | `image`, `audio`, `video` in the asset-class field form |
| Limits | `app_settings` keys `attachments.*` — counts and durations, admin-edited, shipped to devices on `/api/bootstrap`. Byte caps are properties, per kind. |
| Web upload | `POST /log-sheets/{id}/attachments` (session + CSRF); the fill page posts each file separately and keeps ids in hidden inputs |

Three rules in there are security, not tidiness:

- **Access is decided by the owning log sheet, never by knowing an id.** Every method resolves
  the sheet through `LogSheetAccessService.requireVisibleLogSheet` — *including the idempotent
  re-upload path*, which returns an existing row before any other lookup and would otherwise be
  the one unguarded door. A UUID in a URL is not a capability.
- **The declared content type is ignored.** `detectMimeType` reads magic bytes; a client can
  label an executable `image/webp`, and the download route would later serve it back under that
  type. Unrecognised bytes are refused outright, never treated as "unknown but probably fine".
  The one genuinely ambiguous case is Matroska — `MediaRecorder` emits audio and video WebM with
  an identical EBML header — so `resolveWebmType` decides from the *field's* kind, which is
  server-side data rather than client input.
- **Storage keys are generated, never accepted.** `resolveWithinRoot` re-checks that a resolved
  path is still under the root before every read or delete.

The kind a field accepts comes from the **sheet's own frozen `field_definitions_snapshot`**, not
from the request and not from the live class schema. That is what stops a photo being attached
to a numeric field, and it means the answer matches the form the operator actually saw.

### Client-side compression is mandatory, not an optimisation

A tablet camera produces 8–12 MP files. `src/utils/mediaCapture.ts` compresses **before** writing
to IndexedDB, and the original is discarded:

- **Photos** — canvas → `image/webp` at quality 0.8, capped at 1600 px on the long edge
  (`MAX_IMAGE_DIMENSION`). 8 MB → 200–400 KB, still ample to read a gauge face. JPEG fallback for
  anything that cannot encode WebP; a failed encode is an error rather than a silent
  pass-through of the original, which would defeat the point.
- **Audio** — `MediaRecorder` with `audio/webm;codecs=opus`, mono, 24 kbps, hard-capped at 120 s
  (`MAX_AUDIO_DURATION_MS`). The microphone track is stopped on **every** exit path — a live
  track leaves the browser's recording indicator on, which users reasonably read as the app
  spying on them.

### PWA storage

Dexie `version(2)` adds
`attachments: 'id, logSheetLocalId, logSheetServerId, assetId, fieldKey, syncStatus, createdAt'`,
holding **`Blob`s, not base64**. Previews use `URL.createObjectURL` and every URL is revoked on
change and on unmount — leaking them pins whole blobs in memory on a tablet that stays on one
screen for a shift.

The row outlives the blob. `purgeSyncedAttachmentBlobs` drops the bytes of anything safely on the
server for more than 7 days while keeping the metadata, so the field still shows the attachment
and opening it re-fetches. `deleteSyncedAttachmentsForLogSheet` retires rows when the cleanup
pass ages out a local sheet — *only* the synced ones; a pending row carries its own
`logSheetServerId` and must still be delivered.

### Sync: a separate queue, deliberately

**Attachments do not ride inside `POST /api/log-sheets/batch`.** That payload stays small and
atomic; a 400 KB photo inside it means every dropped connection retries the whole shift's
readings.

1. The sheet submits with attachment **ids only** — unchanged code path.
2. On `SUBMITTED`/`DUPLICATE`, `bindAttachmentsToServerSheet` stamps the new server id onto that
   sheet's attachment rows. Until this lands, `getPendingAttachments` skips them: the server keys
   an attachment to a log sheet, so uploading earlier is impossible.
3. `syncPendingAttachments` uploads them **one at a time**. Sequential is deliberate — on a weak
   field link three concurrent uploads are slower than one, far likelier to time out, and would
   hold three blobs in memory at once.
4. The whole pass sits in its own try/catch: a photo that will not upload must never fail a
   log-sheet submission that already succeeded.

**Failure classification is the part worth understanding.** `ApiError` with status 0 means the
transport died — the row is left *completely untouched* (not marked failed) and the pass stops
rather than hammering a dead link, because marking it failed would make a tunnel look like a
rejection. A 4xx other than 401/408 is permanent: the server examined the request and refused it,
and identical bytes get an identical refusal. 401 stays retryable — an expired session is not a
bad payload. 5xx stays retryable but records why it did not go.

**Limits are enforced twice on purpose.** Both clients check counts and durations so the
operator gets a message before wasting a capture; `AttachmentService.upload` checks them again
because a client is not a trust boundary. Counting is per (sheet, asset, field, **kind**), and
the idempotent-retry path is reached before the count check so a retry at the ceiling is not
mistaken for a new file. If you add a rule, add it in `AttachmentService`, not only in a client.

**Video size is controlled at capture time and nowhere else.** A video cannot be cheaply
re-encoded on the device afterwards, so `startVideoRecording` sets 480p / 700 kbps and enforces
a hard byte ceiling *while recording* — the bitrate is a hint an encoder may overshoot. The
client ceiling (15 MB) sits deliberately below the server's (20 MB) so the device truncates
rather than the server refusing the whole clip.

**`retainKnownKeys` normalises attachment values to the canonical object.** The web form posts
repeated inputs and the app posts an object; what lands in `form_data` should not depend on which
client wrote it. Idempotent, so it is safe on every write path.

**The admin panel streams media from its own route**, `GET /log-sheets/{id}/attachments/{attachmentId}`,
not from `/api/attachments/{id}`. The two security chains differ: `/api/**` is stateless and
JWT-only, so a browser session gets 401 and an `<img src>` pointing there shows a broken image.
If you add another panel surface that displays attachments, use the web route and pass the
sheet id — the ownership check depends on it.

**Voiding a sheet does nothing to its attachments.** Void is a soft, reversible status change,
and `requireVisibleLogSheet` checks the operational unit rather than the status — so a voided
sheet still serves downloads and still accepts a queued upload that arrives late. Both are
deliberate: destroying evidence on a reversible action would make the un-void meaningless, and
refusing the late upload would strand the file while leaving a dangling reference in `form_data`.

**A permanently refused upload is parked on the client**, not retried forever — see
`permanentFailure` in the PWA's `storage/attachments.ts`. If you add a new 4xx rejection reason
here, be aware it becomes terminal on the device until someone hits retry.

**Idempotency:** the client-minted UUID is the unique key. Re-uploading it returns 200 with the
existing row and does **not** rewrite the bytes — the first upload won, and a differing retry is a
client bug rather than a correction.

### Storage pressure

`src/utils/storageQuota.ts` calls `navigator.storage.persist()` at startup (a refusal is normal —
browsers grant it to installed PWAs, not casual tabs) and checks `estimate()` **before** opening
the camera. Refusing up front tells the operator to sync while they can still act on it; a failed
IndexedDB write after the shot is taken loses the shot. A browser that reports nothing is treated
as "not low" — refusing a capture because we could not measure the disk would be the worse
failure.

### Orphan files and the sweep

`AttachmentSweepService` deletes files under the storage root that no row references — the usual
cause is a deleted log sheet, whose CASCADE removes the rows and never tells the filesystem.

**The grace period is the safety design, not a tuning knob.** `store()` writes bytes *before* the
transaction commits, so an in-flight upload is indistinguishable from an orphan for a moment. A
file younger than `app.attachments.sweep.grace-hours` (24) is never touched. If you find yourself
lowering it to make a test pass, fix the test instead — the integration test seeds file mtimes to
control age precisely so it never needs a short grace period.

The mirror case (a row whose file is gone) is **counted and shown, never repaired**: deleting
those rows would erase the only evidence that something was lost.

Its integration test is deliberately **not `@Transactional`** — the sweep runs on its own thread
with its own transaction, so rows written inside a rolled-back test transaction are invisible to
it and it would delete files the test considers referenced.

### Groundwork with no client yet

Two things exist server-side with nothing calling them. Do not mistake either for dead code:

- **`location` field type** (`LocationValues`) — validation, canonical storage and panel display
  all work; capture does not exist, so the web fill page renders it **read-only** on purpose. A
  free-text box would invite hand-typed coordinates, which is the unverifiable data the field
  exists to avoid. Display is text with no map link: the panel runs on networks with no internet
  route.
- **`log_sheet_template_guides`** — table, entity and repository only. Guides hang off the
  *template* (a procedure describes the round, not one occurrence) and resolve **live**, unlike
  `field_definitions_snapshot` — a corrected procedure should reach sheets already in progress.
  That asymmetry is intentional. Extend the sweep to its directory when uploads are built.

### Submit rejections are classified, not lumped together

`validateSubmittedFormData` returns outcome **`VALIDATION_ERROR`**, while the other three
rejections in `submitBatch` stay plain `ERROR`. That is not cosmetic: it is the only submit
rejection an operator can fix (by editing values), and the app keys its "correct and resubmit"
control off it. A deleted sheet or an asset mismatch is supervisor territory, and offering the
same control there would imply a power the operator does not have.

Older clients fall through to their default branch and still show the message, so the value is
backward compatible. If you add a rejection reason, decide which bucket it belongs in — an
operator-fixable one that returns `ERROR` recreates the dead end this closed.

The client mirrors `FormDataValidationSupport.isBlank` in `utils/formDataValidation.ts` to
refuse doomed submissions before they are sent. **If you change the blank rules here, change
them there too** — a divergence either lets the dead end back in or, worse, blocks submissions
the server would have accepted.

### Easy things to forget

- **HTTPS** — `getUserMedia` requires it. The existing mkcert/nginx setup already provides it.
- **`capture="environment"`** on the file input is what makes Android open the camera rather than
  the gallery.
- A media field cannot use react-hook-form's `required`: its value is an object once the control
  renders, and every object is truthy. `buildValidationRules` counts ids instead.

- **A `<select>` rendering an existing value must mark one option selected — otherwise the browser picks the first and the save rewrites the field.** The class-field editor's two modals each carried their own hardcoded `<option>` list: ten in create, six in edit. Editing a field whose type was `image`, `audio`, `video` or `location` therefore found nothing to preselect, HTML falls back to the first option, and pressing save silently retyped the field to `number` — turning stored attachment references into values a numeric field can neither validate nor render. The list now lives once, in `FieldDataTypes`, and both modals iterate it (`dataTypeLabels` for create, `editDataTypeLabels` for edit).<br><br>Three parts of the fix are each load-bearing. **The write is checked server-side** (`isValidFor`), because a dropdown is not a boundary and `setDataType(form.getDataType())` previously stored any string posted. **The edit dropdown appends the field's own type** when it is not a standard one (`labelsIncluding`), so a row carrying a legacy `date`/`boolean` is editable rather than retyped — omitting it would recreate the exact bug for those rows. **The whitelist is for writes only**: `FormDataValidationSupport` must keep tolerating unknown types on read, or an older row would become unreadable. Regression: `FieldDataTypeEditIntegrationTest` renders the page for all ten types and asserts exactly one selected option; `FieldDataTypesTest` also parses the PWA's `FieldDataType` union and fails if the two repositories disagree.

- **An arrow between two values must be laid out by flexbox, never by inline text flow — on an RTL page the bidi algorithm decides the visual order, and it decides differently depending on the data.** `<span>old</span> <i class="bi-arrow-left"></i> <span>new</span>` reads correctly right-to-left, so it looks obviously right. But a run of Latin letters or digits inside an RTL paragraph is laid out **left to right**, so the same markup put `old` on the LEFT for Latin values and on the RIGHT for Persian ones, while the arrow glyph — which cannot mirror itself — kept pointing left. Measured in a browser on `/asset-status-requests`, where rows of one table disagreed with each other: `ثبت نشده → OF` rendered correctly and `Idle → ON`, three rows below, was reversed; 5 of 16 rows were wrong. Flex items are ordered by the container's `direction`, not by bidi, which is why `.log-detail-assignment-change` (flex since it was written) never had the bug and why the fix is the `.value-change` class rather than a different arrow icon. Regression: `ValueChangeArrowTest` walks every template and fails on a directional arrow between two values that is not inside a flex container.

- **A log sheet entry has TWO device times and they are not interchangeable: `created_at` is «ثبت داده», `updated_at` is «آخرین ویرایش».** `AssetStatusService.readingsFromSheet` stamped a status-change request with `updated_at`, so the request — and, on approval, `asset_status_history.changed_at` — said the equipment was observed at whatever moment the entry was last touched. Any later edit to the same entry moved it: another field corrected, a supervisor's web edit. The reading time exists precisely so the asset timeline says when the equipment was **seen**, so it must be `created_at`, which does not move. Falls back to `updated_at` only for rows saved before the device recorded a creation time. The trap is that both fields are populated and plausible, and the existing tests set only `updated_at` — so they passed either way and the defect survived a green suite. Any new test about reading time must set the two to **different** values.

- **A client-supplied id that becomes a file name must be REFUSED when malformed, never repaired — "make it safe" quietly maps two ids onto one file.** `AttachmentStorageService.sanitiseId` stripped everything outside `[A-Za-z0-9-]`, so `<uuid>` and `<uuid>!` produced the same storage key. `AttachmentService.upload` writes the file **before** inserting the row, with `REPLACE_EXISTING`; the insert then failed on `uk_attachments_storage_key` and the transaction rolled back — but a filesystem does not roll back, so the first attachment's row survived pointing at the second's bytes. The storage path is global while only the row is scoped to a sheet, so this crossed tenancy: an operator could overwrite a photo on a sheet they cannot see by uploading to their own with the victim's id plus one character. Reproduced end to end, and again over live HTTP. A second variant raised no error whatever — `ABC-…` and `abc-…` are different strings so the unique constraint never fired, yet on Windows both named one file, leaving two healthy-looking rows over one content where deleting either took the other's bytes.<br><br>The fix is `AttachmentIds.canonicalise`: UUID form or 400, lower-cased. A UUID's alphabet is already path-safe, so nothing is ever stripped. Two details are deliberate: the idempotent lookup tries the id **as sent** before the canonical form, so a row written in upper case by an older caller still resolves instead of being re-uploaded into a constraint failure; and `sanitiseId` now asserts rather than repairs, because a defence that lives only in the caller is one refactor away from being absent. Note also that `sha256` is stored and returned but **verified nowhere** — the corruption was undetectable by the system.

- **`register()` for a mobile session is read-then-write, so it needs a lock as well as a unique index — and the index changes how the revoke must be written.** Two concurrent logins both read "nothing active" under READ COMMITTED and both inserted, so one operator held two live tokens; eight simultaneous logins produced eight. `ux_api_sessions_one_active` (V3) now forbids it, but three things had to move with it. **(1)** The index alone turns the race into a *failed login*, so `register()` takes `pg_advisory_xact_lock` per user first — the loser waits, supersedes the winner, and succeeds. **(2)** The revoke had to become a `@Modifying` bulk statement: `ApiSession#id` is `IDENTITY`, so `save()` inserts immediately while dirty entities flush later, and Hibernate runs inserts before updates — loading entities to revoke them left the old row active at the moment the new one was inserted, which the index would reject on *every ordinary re-login*. **(3)** It must revoke every **unrevoked** row, not the **active** ones `findActiveByUserId` returns: a partial index cannot read the clock, so an expired-but-unrevoked row is still indexed and would block the next login forever. Covered by `ApiSessionConcurrencyIntegrationTest` on real threads — a single-threaded test cannot fail here.
